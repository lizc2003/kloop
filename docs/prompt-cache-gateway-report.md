# gateway prompt cache：三个可复现的问题

> 2026-09-07。证据来自 kloop（一个 Rust coding agent）本机 84 个会话 2636 轮真实
> 采样，加上一组针对性的对照实验（9 + 4 个 trial）。本文自足，不需要 kloop 的上下文。
> 测量端点：`/responses`（stream），模型 `gpt-5.6-sol` 与 `gpt-5.5`。
> kloop 侧的完整分析见 `docs/plan/120-prompt-cache-per-round-growth.md` 第六、七节。

我们先排除了自己这边的嫌疑：请求前缀是严格追加的，`prompt_cache_key` 在发，
system 放在 `instructions` 还是 `input[0]` 都试过（对命中率没有影响）。对照实验里
在同一段前缀上连发探针轮，能稳定读回 **98–99%**——**前缀本身没有在断**。

下面三条是排除之后剩下的。

## 一、缓存条目落后好几轮：会话实付的未缓存 input 是理论下限的 2.9 倍

按"每一轮只有**新追加**的 token 该是未缓存的"作下限，拆开 2636 轮实付的
`input_tokens`（未缓存部分）：

| | 轮次 | 未缓存 input | 占超支 |
|---|---|---|---|
| 下限（怎么都得付） | — | 40.9M | — |
| 健康轮（命中率贴着 `1 - delta/total`） | 1421 | 1.5M | 2% |
| **命中了，但远低于该有的水平** | **534** | **42.1M** | **55%** |
| **整条前缀没命中** | **369** | **33.5M** | **43%** |
| 实付合计 | 2636 | 118.0M | — |

超支 77.1M tokens。其中最大的一块是那 534 轮——它们**命中了**，所以不是"缓存没
建立"，但命中的量对不上当前前缀。拿 `cache_read_input_tokens` 去比更早各轮的
prompt 长度，**232 轮精确对上了 2–30 轮之前那一轮**：

```
round 11: prompt 32956, cache_read 13824  ==  round  3 的 prompt (13765)
round  7: prompt 17286, cache_read 10752  ==  round  5 的 prompt (10989)
round  6: prompt 16665, cache_read  7680  ==  round  0 的 prompt  (8216)
```

（"对上 1 轮之前"的只有 1 例，因为那就是正常情况，已划进健康轮。）`cache_read`
一律是 128 的整数倍（7680=60×128、10752=84×128、13824=108×128）。

读作：**不是每一轮的前缀都被写进缓存**，落后期间追加的一切，下一轮全部重付。

对照实验里也反复出现整条不命中的轮次（同一个 key、严格追加、每轮间隔 3 秒，前后
轮都正常命中）：

```
r0 base   prompt 21025   cache_read     0
r1 +10k   prompt 31453   cache_read 20224   <- 正常：命中 r0
r2 +10k   prompt 41872   cache_read 30464   <- 正常：命中 r1
r3 +10k   prompt 52492   cache_read     0   <- 前一轮刚命中过，这一轮整条丢
```

实验里"落后好几轮"的样本都伴随着传输错误重试，不干净，所以第一条的直接证据以上面
生产采样的 232 轮为准。

**希望确认**：前缀写入是否有采样/限流/延迟？同一 `prompt_cache_key` 下连续请求，
写入策略是什么？上面 r3 那种"前一轮刚命中、下一轮整条丢"是预期行为吗？

## 二、`cached_tokens` 有假阳性：从未发出过的内容被报成命中

COLD 对照：内容是当场生成的随机词序列（此前从未发出），`prompt_cache_key` 也是
全新的，第一次发出。`gpt-5.5` 上 5 次里有 2 次报出命中：

```
COLD control: input=21605  cached=19072 (88%)
COLD control: input=21595  cached=19840 (92%)
```

（`gpt-5.6-sol` 上 4 次 COLD 全部 0%，是干净的。）

最可能的解释是网关内部重试之后，把第二次尝试的 usage 报了出来。如果是这样，
**`usage` 的口径需要明确**：它报的是这次调用的合计，还是最后一次内部尝试的？
按调用计费的话，这个数字直接影响账单核对。

## 三、`prompt_cache_key` 不是隔离边界，缓存按内容命中

同一账号下，把完全相同的请求体换一个**全新的** `prompt_cache_key` 重发，仍然命中：

```
（约 25 分钟前用 key A 发过同一段内容）
key B, r0 首轮:  prompt 21656  cache_read 18816 (87%)
key B, r0 首轮:  prompt 21568  cache_read 19456 (90%)
```

这一条对我们只是实验坑（复用随机种子会让整个实验去测上一次跑留下的缓存，必须每次
运行重新随机内容）。但它说明 `prompt_cache_key` 只是路由亲和提示，不构成隔离。
**希望确认**：跨账号是否也如此？如果是，这是需要单独评估的问题。

## 复现

一次性脚本，未入库，形状：

1. 生成一段 ~21k token 的随机词填充（**每次运行重新随机**，否则会命中上次的缓存）。
2. 走 `/responses`，`stream: true`，`store: false`，带 `prompt_cache_key`。
3. 严格追加地一轮轮发，记录每轮的 `input_tokens` 与
   `input_tokens_details.cached_tokens`。
4. 两臂对照：一轮追加 30k vs 三轮各追加 10k，之后在同一个 ~52k 前缀上连发
   200 token 的探针轮；两臂逐轮交替、每个 trial 换先后手。

跑的时候会遇到 `502` / `504` / `upstream_error` / `gateway_concurrency_limit`，
需要重试；**重试过的轮次必须单独标记并排除**（重试本身会制造命中，见第二条）。
同一臂内 `input_tokens` 必须单调，网关过载时出现过非单调（误报），那批数据作废。

## 我们不需要什么

- 不需要 `previous_response_id` 有状态模式或服务端压缩——kloop 自己管上下文。
- 缓存命中率对我们是成本问题，不是正确性问题；上面三条里只有第三条可能不是。
