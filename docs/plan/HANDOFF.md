## 二、当前状态(plan 1–12 全部完成)

**结构**:Cargo workspace,七 crate,到 core 为止严格单链,其上两个平级前端 + 一个协议级旁支(详见 `kloop/README.md` Layout 节):

## 三、沉淀的实现教训(新代码沿用)

1. 递归 async 的 Send 推断有共归纳盲区:递归边界必须是签名级类型擦除(`execute_tool` 返回 `Pin<Box<dyn Future + Send>>`)+ 子 agent `tokio::spawn` 成独立任务。
2. offload 编号用进程级全局 AtomicUsize——父子 agent 共用目录,per-实例计数会互相覆盖。
3. 子 agent(depth>0)的文本不流式输出到主 UI,产出走 tool result。
4. cc 的公式移植前先想小参数退化(predictive 负阈值教训)。
5. 压缩/重写类操作失败时必须保证原数据原封不动,测试锁死这一点。
6. 追加型文件的坏尾必须**物理**截断再续写:只做逻辑跳过的话,追加会和半行拼接成一行,之后的数据全部不可达(plan 7 潜伏 bug,7b 修复)。
7. 磁盘 schema 是基础模块里最难改的部分:演化字段(id/parent/ts)要在有存量文件之前落上;性能工程不改格式,可以后补。
8. 安全判定别手写 shell 拆分:字符串 replace/split 版一天内被找出三个注入洞(`$()`、换行、单 `&`),补丁式修补追不完;正解是 tree-sitter 白名单遍历 + "解析不了 = 不可分析 = 永不自动放行"。凡是"分类后放行"的逻辑,分类器必须是白名单而非黑名单。
9. 参考实现互相矛盾时以官方 SDK/spec 为准,不看谁的代码顺眼:MCP stdio 分帧 claw-code 用 LSP Content-Length(错),cc 包的官方 SDK 用换行分隔 JSON(对);跟真实生态互操作的协议细节,权威来源只有 spec 和官方 SDK。
10. 外部注入的名字要过本系统最窄的语法关:MCP 工具名进了权限规则语法(alnum+`_`),消毒时 `-` 也得折成 `_`,否则"允许并保存"写出的规则下次启动解析失败。
11. plan 文件里提炼过的参考语义是二手信息,实现语义契约时要回源核对一次:plan 11 写"退出码非 0 阻断",但 cc/codex 实际是 exit 2 才阻断(理由走 stderr)、其他非 0 = 非阻断失败——"非 0 即阻断"把 hook 自身出错误读成策略阻断,与 fail-open 原则矛盾,上线当天返工。教训 9 说权威来源是 spec 和官方实现,这里的推论是:自己早前的调研笔记也不算权威来源。
12. 抄参考实现的形态前先量它的真实移植成本,`[patch]` 段只是线索不是结论:codex tui 的 fork 增量其实极小(ratatui 仅 +`expose set_viewport_area`,crossterm 仅 +`query_fg/bg_color` 主题探测;scrolling-regions 在上游 0.29 本来就有),真正重的是 vendor 进仓库的 ~35KB CustomTerminal(ratatui Terminal 魔改副本)+ insert_history 自写 scroll-region 命令那套机制。对最小可用,这个体量本身就是不抄的理由;全屏 + 自维护缓冲的决策不变。**(plan 38 切片 0 已推翻末句)**:inline 经核实是**中等工程,非当初以为的「太重」**——上游 ratatui 0.29 原生 `insert_before` + `scrolling-regions` feature 就够,不必 vendor CustomTerminal,不必 fork。当初的误判正是本教训的反面案例:把"vendor 副本很重"错推成"inline 路线很重"。真正躲不掉的只有 CPR/stdin 并发这一集成陷阱(教训 38)。
13. 形态赌"模型行为"时,验收必须覆盖最弱目标模型,并为它留一条**声明过的**通道:plan 16 赌模型肯对 tools 数组外的名字发 tool_use——sonnet-5 行,gpt-5.4-mini 任何措辞都拒绝(模型被训练成只调声明过的工具,不是提示词能修的);解法不是换形态,是加 call_tool 信封兜底 + 分发入口拆包,主路径与权限/hooks/并发/UI 四层都只见真名。cc 旧版的 ExecuteExtraTool 中转看似绕弯,其实就是这个兜底。
14. 抄参考形态前看两个信号:**收敛**与**方向导数**。plan 18 里 cc 与 codex 在"fork = 物理复制前缀,不做跨文件重放链"上独立收敛——两家用完全不同的存储(单文件树 vs 文件级血缘标签)得出同一取舍,这比任何一家的单独选择都有说服力;反面是 codex 的 `thread/rollback` 还在代码里但上游已标 DEPRECATED、正收敛到 fork-by-turn-id——参考库里"存在"不等于"值得抄",一个 API 的存续方向和它本身同样重要。
15. 移植来的启发式判定表不等于完备,要拿本系统最常见的真实场景回测:plan 19 把 codex 的 sandbox-denial 关键词表原样移植后,实测"断网沙箱里 curl"——最常见的网络拦截——报 `Could not resolve host`,表内七个关键词全不命中(codex 自己也有这个洞),模型只能靠猜;修法是带条件的扩展(仅 network_disabled 时 DNS 失败算证据),既补洞又不放大误报。同理 seatbelt 的行为(拦截报错形态、继承 fd 是否受限)全部实测过再写进设计,两处猜测都会猜错(继承 fd 其实可跨界写,后台输出文件因此不用开洞)。
16. plan 里对某机制"成本"的假设,开工时要按**当前真实架构**核算一遍,不能照抄:plan 22 备忘假设子 agent 回灌"靠 JoinHandle 终态回调就够",听着便宜;但现有 task 是**同步 `handle.await`**(parent 阻塞等着、final_text 已作 tool_result 直接回),这个架构下回灌**没有独立价值**——要它有意义得先建整套异步派发(spawn 立即返回 + 完成侦测 + autowake + 注册表),那是 plan 17 片 6 明说"别提前抽象"的大件。回源(教训 14)进一步印证:cc 与 codex 独立收敛于"子 agent 回灌整套依赖异步派发"。结论:一个 plan 的两个消费者若成本差一个数量级,开工时要拆开、只做够独立闭环的那半(step 边界注入机制 + 用户 steering),另半连同它的前置一起挂账留独立 plan。教训 11 说"plan 是二手信息",这里的推论是:连 plan 对成本/依赖的估计也算二手,要对着现有代码复核。
17. 一个参考实现看着吓人的复杂度,开工前要**归因**:是功能本质需要的,还是它选的底座(引擎/框架/平台)连带的?两者可差一个数量级,砍掉后者只需换底座、不是硬啃。plan 24 code mode:codex 版核心引擎 ~3400 行 + sidecar ~3000 行 + `cell_actor` 一半是 observation 状态机 + 每 cell 独立 OS 线程 + `IsolateHandle` 强杀——**这些复杂度绝大多数是 V8(40MB,得移出主二进制 + 管生命周期)催生的,不是 CodeAct 本身要的**。换 rquickjs(几百 KB、进程内、原生 async future↔Promise、内建内存/超时限)直接删掉这一多半,还顺手补上 codex 缺的内存上限。归因的抓手:① 查它选这个底座的**理由**(codex 用 V8 是血统 + Cloudflare 平台本就是 V8 isolate 的红利,kloop 一个前提都不占);② 把**收益**拆到底座上——Cloudflare 自己的数字说"工具→TS API 省 81% token",证明 token 收益来自渐进披露、与 V8 无关(那半 plan 16 已有)。教训 12/16 是"量成本别照抄",这条是其推论:成本要**拆到底座**再量,换底座能让"最重的 plan"的实付复杂度掉一半。真正引擎无关的必然解(嵌套工具重入既有 gate、异步 Promise 桥、TS 声明喂模型、JSON 值边界)才照搬。

19. 两条来自 plan 27 的推论。**(a) 同预算的两套机制必须"组合"而非"叠加后互相拆台"**:defer(渐进披露)和 code-mode(工具→TS API)都在省同一份上下文预算。plan 27 备忘原倾向"defer 开时 `run_program` description 仍塞 source 工具的**全量 TS**",听着是"code-mode 作为 defer 的另一解";但那等于把 defer 刚撤下的 N 份 schema 换个地方(一个工具的 description)灌回每轮请求——**code-mode 悄悄拆了 defer 的台**。回源 codex:它 defer 开时把 MCP 工具降级成 `ALL_TOOLS` 紧凑 name+desc,**不给全量 TS**(`build_mcp_tool_exposure`:`search_tool_enabled` 时全部进 deferred)——两套机制**组合**(defer 也压 code-mode 面),不叠加。判据:一个新 surface 消费某省预算机制时,先问"它会不会把另一套省下的又吐回来";会,就让那套机制也作用到新 surface 上。这是教训 11(plan 备忘二手、回源纠偏)+ 14(收敛信号)的一个具体落点。**(b) 门要分"发现门"与"安全门"**:defer 的 `locked()`(没 tool_search 过就弹回)是**发现门**——防的是"模型不知道 schema 瞎调";deny/权限/沙箱是**安全门**。program 调 deferred 工具时该跳过前者(工具已由 `run_program` 暴露给 program=对 program 而言已"发现")、绝不跳过后者。`ToolCtx.from_program` 只关掉 `locked()` 一层,其余全走。判据:给某调用来源开"绿色通道"前,先把沿途每道门分类成发现/安全,只有发现门能按"来源已具备该能力"豁免。

21. **要给循环加"外部事件唤醒"前,先看它现有的事件流里有没有一个已经会因同一件事醒来**。plan 26 autowake:异步子 agent 完成后要让空闲的 TUI 主循环起一个交付 turn,我一开始设计了一条新的 `Ui::request_wake` 控制通道(子完成→ChannelUi 发个新 AutoWake 事件→唤醒 select)。但子完成本就会调 `ui.agent_end`,而 `agent_end` 已经是一条走同一个 mpsc 的 `AgentEvent`——它自然会唤醒 ui_loop 的 `select`。于是**新通道是多余的**:真正缺的不是"唤醒信号"而是"醒来后判断要不要起 turn 的条件"(`autowake_ready = 空闲 且 inbox 非空`),把这个纯函数放在每批事件处理之后即可,还顺带天然覆盖了 race(子在父末次 drain 之后、TurnEnded 之前完成——TurnEnded 也是个 AgentEvent,照样把循环唤醒来复查)。判据:实现"X 发生时唤醒循环 Y 去做 Z"前,先列出 X 发生时 Y 已经会收到的信号;若其中任何一个已经会唤醒 Y,就只写"醒来后判断是否该做 Z"的条件,别新拉一根线。这也让 autowake 保持成 TUI 本地关注点、不污染 core 的 `Ui` trait。
22. **收敛的"必然解"照抄形状,但粒度用本项目地基能达到的最优;别把参考库的粒度当成必然解的一部分**。plan 17 片 3 子会话落盘:cc/codex 收敛在"每子 agent 独立文件 + 文件内元数据记父",这个**形状**照抄;但两家的父指针都是 **session 级**(cc 每消息 sessionId、codex SessionMeta.parent_thread_id),那是它们各自地基的产物(cc 的树、codex 的 SQLite 边)。kloop 是单文件线性 rollout + 现成的行 id(`{stem}#{seq}`),于是同一个"记父"能免费做到**行级**——子会话首行 `subagent_of` 指回父**触发 task 的那一行**,审计时能精确定位而非只知道"属于某会话"。判据:回源拿到收敛解后,把它拆成"形状"(必然,照抄)和"精度/实现"(它的地基决定,不一定是你的最优),后者按自己地基重估——有时你的地基支持更细。**附带一个字段语义分界**:跨文件血缘指针不止一种——fork(复制父前缀、`parent` 指分叉点、是 replay 边界)和 subagent(全新独立历史、`subagent_of` 记归属、replay 无关)是两回事,硬塞一个字段会让 list 把子会话误标成 fork;按语义分成两个 skip-if-None 字段,`session_origin` 里定优先级,各自的 remeta/resume 记得清零对方。
23. **参考库把一个事件拆成两个、而你的架构本可统一时,先看这个"拆"有没有解锁更富的 payload——有就照拆,别贪图统一**。plan 17 片 5:cc/codex 都把"回合结束"拆成 `Stop`(主)/`SubagentStop`(子),而 kloop 一个子 agent = 一次 `run_turn`,`post_turn` 本可统一表达两者(post_turn 恰好每子触发一次)。统一更省,但拆开后 `subagent_stop` 能带**子 agent 专属的富 payload**——子会话 transcript 路径(片 3 刚落)+ 结果摘要——这是通用 `post_turn` 塞不进去的(塞了就污染主 agent 的 post_turn 形状);且"主 agent 结束"和"某个子 agent 结束"本就是 hook 脚本想分别挂的两件事。判据:遇到"参考拆、我可合"的形状差异,别只按"我的地基更省"就合;问"拆开的那个分支能不能带只属于它的数据/语义,而合并会逼它挤进通用形状"——能,就照拆。这是教训 22 的另一面:22 是"照抄形状、粒度按地基做更细"(片 3 血缘做到行级);23 是"照抄形状、别为省事把它抹平"(片 5 保住分裂)——两条合起来 = **形状照收敛,增删都要有"这带来能力/精度"的实据,不为省事也不为整齐**。
24. **回源看一个机制,别停在"它有这个类/API",要追它的输入/来源是否真接通——参考库里整套代码都在、却因为来源是硬编码占位而从不生效,照抄就是建个 no-op 摆设**。plan 24 token budget:cc 的 `Budget` 类、`spent()/remaining()/assertCanSpend()` API、每次 agent() 后 `addOutputTokens` 累加——**全都在**;但 `budget.total` 在生产 host 里是硬编码 `null`(`ports.ts:61`/`service.ts:137`,注释"未来从 settings 读"),"+500k" 解析器存在却没接进来。于是 `remaining()` 恒 `Infinity`、硬顶永不触发——**整个 budget 是个为未来预留的 no-op**。plan 27 说"code-mode 只剩 token budget",若照"cc 有 budget"就抄,kloop 会造一个同样空转的摆设(还得先无中生有一个"预算来源")。回源坐实后改判:真正生效的失控保护是 caps(`MAX_TOTAL_AGENTS`/`MAX_ITEMS_PER_CALL` 硬抛),那才照抄。判据:回源一个"可配置/可驱动"的机制,追到它 total/config/source 的**实际赋值点**,确认不是 null/占位;是占位就说明连参考库自己都没真用它,你八成也不需要,或需要先补它缺的来源(而"补来源"往往是另一个 plan)。这是教训 11(plan 是二手)+ 14(收敛才抄)的延伸:**"参考库里存在" ≠ "生效",别把占位当收敛解**。

25. **一轮全项目自审(2026-07-14,7 路并行 agent 精读 + 逐条回码复核)沉淀的几类可复用 bug 模式**——都是"单测过、clippy 绿"却仍潜伏的正确性/安全洞,新代码要照防。**(a) 处理外部/多字节文本时绝不按字节偏移切串**:`html.rs` 的 `decode_entity` 用 `rest[..12]` 找 `;`、`sse.rs` 三 adapter 逐 chunk `from_utf8_lossy`——前者在"`&`+十几个 ASCII+汉字"上 panic(来自 web_fetch 的不可信 HTML,中文页极常见 = 可达 DoS),后者把跨 TCP 分块的多字节字符拆成两个 U+FFFD **污染进历史/rollout 的正文**。正解:按 `char_indices`/完整帧切,不裸切字节;流式解码的正确切点是"缓冲原始字节、只解码完整帧"——帧分隔符(`\n\n`/`\r\n`)是 ASCII,保证不落在多字节序列内部。中文负载把这类 bug 从"理论"变"必现"。**(b) 安全比较要匹配文件系统的真实语义**:`path_is_sensitive` 与 deny glob 都大小写敏感,但本项目跑在 macOS 默认大小写不敏感 APFS 上——accept-edits/bypass 下 `write_file(".GIT/hooks/pre-commit")` 判定不敏感→自动放行→磁盘实为 `.git/hooks/pre-commit`→下次 commit 提权。判据:凡"路径→是否敏感/是否命中规则"的比较,先问运行平台的 FS 折不折叠大小写,折叠就得 `to_ascii_lowercase` 再比(Linux 上 `.GIT` 是不同文件、不折,`cfg!(macos/windows)` 门控)。**(c) detached task 持 strong `Arc<Owner>` 会把 Owner 的 `Drop` 清理变成死代码**:后台 shell 的 `monitor` 持 `Arc<BackgroundShells>`,于是"有 shell 在跑→Arc 不归零→Drop 不发火→全退出后才发火但 status 全非 Running→`kill_group` 分支永不执行",session 结束时残留进程无人回收(server 模式泄漏)。判据:需要"owner 被释放就触发 teardown"时,detached task 必须持 `Weak`、用时 `upgrade()`(拿不到就是 owner 已走、teardown 已由 Drop 负责)。**(d) 深度/资源受限的解析器耗尽预算时必须 fail-closed**:`analyze_bash` 的 `bash -c` 解包超 `MAX_UNWRAP_DEPTH` 后把没展开完的 `["bash","-c","rm -rf /"]` 当**可信平文命令**,`argv_is_dangerous` 只看 `bash`→漏、bypass 模式自动执行,破了"安全检查 bypass 免疫"。正解:上限处仍是包装形态就返回 `Opaque`(不可信、永不自动放行)。**(e) 续跑/累积型交付别只取末次**:截断续写恢复的 `final_text` 只取末轮文本,而子 agent(`stream_text=false`)交付**只**经 `final_text`——长答案撞 max_tokens 后前段永久丢;需累加每轮。**统法**:这五条的共性是"正常路径都对,边界/不可信/平台差异处才露",单测容易只覆盖正常路径;写这类代码时主动列"多字节输入、大小写变体、owner 提前释放、预算耗尽、被截断"五种边界各补一个测试。(修复见 commit `bfb3efc`/`4789d63`/`625e1f6`;低危与重复代码清理挂账。)

28. **跨生态翻译一层标识符时做"开放映射"(命中改写、未命中透传),不是"封闭映射"(白名单丢弃)**。plan 28 片 3 `allowed-tools`:公开 skill 用 cc 工具名(`Read`/`Bash`),kloop 用 `read_file`/`bash`。若只"映射表命中才收、未命中丢",kloop 原生名(`read_file`)和 MCP 名(`srv__x`)会被误丢 → fork 子 agent 工具限制过紧、废掉 skill。正解 = 映射已知 cc 名 + **未知名原样透传**(同时认下载来的 cc 名与 kloop 原生/MCP 名),再 fail-soft(限制过紧只是少个工具、模型报"用不了",不静默腐蚀)。cc scope 限定 `Bash(git:*)` 剥成裸 `bash`(kloop 靠权限规则 scope、不靠 skill 工具表)。判据:把外部生态的标识符翻译进本系统时,默认透传未识别的、只改写认识的——封闭白名单会把"本系统原生就对的"也误杀。是教训 26(要兼容的是规范不是实现)在"标识符层"的落点。

29. 三条来自 plan 29 片 2(工具读图 + `ToolResult` String→blocks)。**(a) 把一个到处被读成 `String` 的字段升级成"文本或结构"二态,选序列化能对齐外部 wire 的 enum,前向兼容白送、改动面最小**:`ToolResult.content` 从 `String` 撑成 `enum ToolResultContent{Text(String),Blocks(Vec)}` `#[serde(untagged)]`——Anthropic 的 `tool_result.content` 本就是 `string|array` 二态,于是 Text 序列化裸字符串(旧 rollout `content:"…"` **反序列化天然回 Text**,零迁移)、Blocks 序列化数组(anthropic 轨零改动)。配 `From<String>`/`From<&str>`(构造点 `.into()` 不改)+ `as_text()->Cow`(所有"只要文本"的下游[offload/hook/codemode/降级占位]一个方法收口)。**执行层只让唯一能返非文本的工具(read_file)升级返回类型、其余仍返 String 统一包 Text**,把改动挡在一个 arm。判据:给贯穿字段加"第二形态"时,优先找一个序列化恰好对齐你主轨 wire 的容器(untagged enum 常中),旧数据前向兼容和主轨零改动就一起白送;别改成"所有旧站点都要遍历"的形态(如裸 `Vec<Block>`,String 站点全炸)。是教训 28(a)(canonical 选下游白嫖最多的形状)在"字段升级"方向的对偶。**(b) 回源"哪家怎么做"要读到它对外发的真实形态,别停在 plan 备忘的一句概括**:plan 回源结论记"cc 的 MCP 结果可带 image",据此以为 cc 靠 MCP 读图;真读 `FileReadTool.ts:650-666` 才发现 cc 是**一个 Read 工具判 MIME/magic 读文本/图/PDF/notebook**,读图直接返 `tool_result.content:[{type:image}]`——两家在"单 Read 判 MIME(cc)vs 单开 view_image(codex)"上是分歧,plan 备忘把 cc 侧记漏了。用户连问三次"cc 是怎样的",逼出逐处真读。判据:设计决策要落在"某家怎么做"上时,`grep` 到那家的**工具定义/wire 序列化点**亲眼看,plan 的一句话概括常漏掉主路径(教训 11 二手,这次的具体形态:漏的是"主工具本身就干这事")。**(c) 主家为边缘轨做的省事降级,搬到你这条轨是正经副轨时要重估——降级方案按"该轨在你项目的地位"选,不照抄主家**:tool_result 内嵌图,cc 的 openai-chat 轨直接**丢弃**图(cc 主轨是 Anthropic,Chat 是边缘轨,丢了无所谓);但 openai-chat 对 kloop 是**正经副轨**,丢弃=该轨读图彻底失效。故破例不随 cc、取 codex 的**搬运**(tool 消息留占位 + 图另建紧随 user 消息带 data URL,信息不丢)。落地还白捡一个结构红利:kloop 一轮 tool_result 本就聚在一条 `Message::tool_results`,`to_openai_messages` 循环内 tool 消息先 push、图攒到末尾随 user 消息 push,**天然满足** OpenAI"tool 消息紧跟 tool_calls、user 消息延后"的排序,不用 codex 跨 Message 的 `pending` 缓冲。判据:抄某家的"降级/丢弃"策略前,先问"这条轨对它是主是边、对我是主是边"——同一条轨在两个项目的地位不同,主家能丢的你可能丢不起。附真机验收细节:验收 prompt 别用"secret token"这类词(gpt-5.4-mini 误判为敏感直接拒答,与 kloop 无关),换中立措辞("转写大号粗体标题")即读出;是教训 18 真机验的一个坑点。

30. **回源一个有争议的能力,除了"谁做了/怎么做",一定要问"谁明确**不**做、以及他不做换来了什么原则一致性";三家相反(非收敛)时,"不做"也是一个正当结论,常是更保守项目的选择**。plan 30 write_stdin(往活的后台进程写 stdin):codex 唯一建了(`unified_exec`,且 `write_stdin` 的 `pre_tool_use_payload → None` **放行**——会话在 `exec_command`/spawn 那一刻过一次门就够);cc、claw **明确不建**(cc 所有 `stdin.write` 全是内部用途、无面向模型的工具,后台模型是"auto-backgrounded a long-running **blocking** command",观测型非交互)。关键:cc 的"不建"不是没想到,是**功能层的取舍**——它有更强的权限/审计契约(每条 bash 都过分类器),而"往已在跑的解释器写 stdin"埋三坑:① 不过门的输入通道 = REPL 逃逸(后台 `python3 -i` 过了 bash 门,再 `write_stdin` 喂 `os.system("rm -rf")`,喂进去的内容永不面对分类器);② 裸管道对真交互程序(`ssh`/`psql`/`vim` 探 isatty/行编辑)是半吊子,要 PTY 才不脚枪(codex 专门有可选 `tty` 参数就是此故);③ 跨 turn 的活会话是隐藏可变状态,难审计/resume/压缩。codex 与 cc 是**相反的赌注**,不是"codex 领先、cc 没跟上"。**选边的锚点是本项目已有的核心契约**:kloop 的权限门比 codex 强(危险 bash 会问),而 write_stdin 放行会在门后开一条逃逸道,违背 kloop"门上看到的=实际跑的"——故选 cc,plan 30 标不做(要交互走"重构成一次性命令 `python3 -c`/heredoc/管道",kloop 今天就支持;真有痛感再重启,且届时连 PTY 一起做 + 重估权限门)。判据:是教训 14(独立收敛才照抄)的反面——**分歧时别默认"有的那家是进步",按本项目最硬的契约(这里是权限可审计性)仲裁,可能选"不做";而"某家明确不做"要追它不做换来的一致性,那是和"某家做了"同等的信息**。

31. **一道"每调用一问"的保护门,遇到一次碰一堆目标的新消费者时,要把同一条判定改写成对结果集的过滤,别硬塞进 ask;且复用已有规则词汇,让用户一条规则覆盖所有读路径**。plan 31 grep/glob 路径级保护:kloop 的 read deny(`read_file(**/*.pem)`)+ 敏感路径(`.env`/`.ssh`/…)原来只在 read/write/edit_file 的**权限门**跑(一路径一问),而 grep/glob 一次遍历读一整棵树、顺手把 `.env` 内容读进上下文——门那套"单路径 ask"粒度根本不适配(一次问几百个文件?)。正解照 cc 的 `getFileReadIgnorePatterns`:同一条"读可及性"判定(`Permissions::read_path_blocked` = 敏感 **或** 命中 `read_file` deny)在 grep/glob **收集结果时对每个命中文件跑一遍、命中即剔除**,末尾报 `[N path(s) hidden]`(不静默骗模型"没有")——是**输出过滤**不是 ask。两个可复用判据:**(a) 保护的"表达形态"跟着消费者的"作用粒度"走**——门(单调用)用 ask,批量读(树遍历)用结果集减法;同一条安全判定可以有两种投影,别因为门是 ask 就逼树遍历也去 ask。**(b) 扩一条保护到新工具时,复用已有规则词汇、别新造平行规则形**:痛点原话是"用户写了 `read_file(**/*.pem)` deny 期望它挡住所有读",正解是让这条 read deny 对 grep/glob **统一生效**(cc"读忽略集,读类工具统一尊重"),而不是逼用户再学一条 `grep(**/*.pem)`——`Rule::matches_path("read_file", …)` 原样复用,连 whole-tool `read_file` deny 也顺带命中全部(read_file 被 deny 时 grep 读内容是同一能力)。附一条模式覆盖纪律:只有 `allow_all`(`--mock`/测试)不过滤,`--permission-mode bypass`**仍过滤**——对齐权限门 deny/safety check 的 bypass 免疫(读 deny + 敏感是安全属性,不被 bypass 盖过)。是教训 25(b)(安全比较要匹配真实语义)+ 教训 19(b)(发现门 vs 安全门分类)的合流:同一安全判定,按消费粒度换投影,别新造门也别漏掉旁路读口。
