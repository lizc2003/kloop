## 二、当前状态(plan 1–12 全部完成)

**结构**:Cargo workspace,七 crate,到 core 为止严格单链,其上两个平级前端 + 一个协议级旁支(详见 `kloop/README.md` Layout 节):

## 三、沉淀的实现教训(新代码沿用)

1. 递归 async 的 Send 推断有共归纳盲区:递归边界必须是签名级类型擦除(`execute_tool` 返回 `Pin<Box<dyn Future + Send>>`)+ 子 agent `tokio::spawn` 成独立任务。
2. offload 编号用进程级全局 AtomicUsize——父子 agent 共用目录,per-实例计数会互相覆盖。
3. 子 agent(depth>0)的文本不流式输出到主 UI,产出走 tool result。
4. cc 的公式移植前先想小参数退化(predictive 负阈值教训)。
5. 压缩/重写类操作失败时必须保证原数据原封不动,测试锁死这一点。
6. 追加型文件的坏尾必须**物理**截断再续写:只做逻辑跳过的话,追加会和半行拼接成一行,之后的数据全部不可达(plan 7 潜伏 bug,7b 修复)。
7. 磁盘 schema 是基础模块里最难改的部分:演化字段(id/parent/ts)要在有存量文件之前落上;性能工程不改格式,可以后补。
8. 安全判定别手写 shell 拆分:字符串 replace/split 版一天内被找出三个注入洞(`$()`、换行、单 `&`),补丁式修补追不完;正解是 tree-sitter 白名单遍历 + "解析不了 = 不可分析 = 永不自动放行"。凡是"分类后放行"的逻辑,分类器必须是白名单而非黑名单。
9. 参考实现互相矛盾时以官方 SDK/spec 为准,不看谁的代码顺眼:MCP stdio 分帧 claw-code 用 LSP Content-Length(错),cc 包的官方 SDK 用换行分隔 JSON(对);跟真实生态互操作的协议细节,权威来源只有 spec 和官方 SDK。
10. 外部注入的名字要过本系统最窄的语法关:MCP 工具名进了权限规则语法(alnum+`_`),消毒时 `-` 也得折成 `_`,否则"允许并保存"写出的规则下次启动解析失败。
11. plan 文件里提炼过的参考语义是二手信息,实现语义契约时要回源核对一次:plan 11 写"退出码非 0 阻断",但 cc/codex 实际是 exit 2 才阻断(理由走 stderr)、其他非 0 = 非阻断失败——"非 0 即阻断"把 hook 自身出错误读成策略阻断,与 fail-open 原则矛盾,上线当天返工。教训 9 说权威来源是 spec 和官方实现,这里的推论是:自己早前的调研笔记也不算权威来源。
12. 抄参考实现的形态前先量它的真实移植成本,`[patch]` 段只是线索不是结论:codex tui 的 fork 增量其实极小(ratatui 仅 +`expose set_viewport_area`,crossterm 仅 +`query_fg/bg_color` 主题探测;scrolling-regions 在上游 0.29 本来就有),真正重的是 vendor 进仓库的 ~35KB CustomTerminal(ratatui Terminal 魔改副本)+ insert_history 自写 scroll-region 命令那套机制。对最小可用,这个体量本身就是不抄的理由;全屏 + 自维护缓冲的决策不变。
13. 形态赌"模型行为"时,验收必须覆盖最弱目标模型,并为它留一条**声明过的**通道:plan 16 赌模型肯对 tools 数组外的名字发 tool_use——sonnet-5 行,gpt-5.4-mini 任何措辞都拒绝(模型被训练成只调声明过的工具,不是提示词能修的);解法不是换形态,是加 call_tool 信封兜底 + 分发入口拆包,主路径与权限/hooks/并发/UI 四层都只见真名。cc 旧版的 ExecuteExtraTool 中转看似绕弯,其实就是这个兜底。
14. 抄参考形态前看两个信号:**收敛**与**方向导数**。plan 18 里 cc 与 codex 在"fork = 物理复制前缀,不做跨文件重放链"上独立收敛——两家用完全不同的存储(单文件树 vs 文件级血缘标签)得出同一取舍,这比任何一家的单独选择都有说服力;反面是 codex 的 `thread/rollback` 还在代码里但上游已标 DEPRECATED、正收敛到 fork-by-turn-id——参考库里"存在"不等于"值得抄",一个 API 的存续方向和它本身同样重要。
15. 移植来的启发式判定表不等于完备,要拿本系统最常见的真实场景回测:plan 19 把 codex 的 sandbox-denial 关键词表原样移植后,实测"断网沙箱里 curl"——最常见的网络拦截——报 `Could not resolve host`,表内七个关键词全不命中(codex 自己也有这个洞),模型只能靠猜;修法是带条件的扩展(仅 network_disabled 时 DNS 失败算证据),既补洞又不放大误报。同理 seatbelt 的行为(拦截报错形态、继承 fd 是否受限)全部实测过再写进设计,两处猜测都会猜错(继承 fd 其实可跨界写,后台输出文件因此不用开洞)。
16. plan 里对某机制"成本"的假设,开工时要按**当前真实架构**核算一遍,不能照抄:plan 22 备忘假设子 agent 回灌"靠 JoinHandle 终态回调就够",听着便宜;但现有 task 是**同步 `handle.await`**(parent 阻塞等着、final_text 已作 tool_result 直接回),这个架构下回灌**没有独立价值**——要它有意义得先建整套异步派发(spawn 立即返回 + 完成侦测 + autowake + 注册表),那是 plan 17 片 6 明说"别提前抽象"的大件。回源(教训 14)进一步印证:cc 与 codex 独立收敛于"子 agent 回灌整套依赖异步派发"。结论:一个 plan 的两个消费者若成本差一个数量级,开工时要拆开、只做够独立闭环的那半(step 边界注入机制 + 用户 steering),另半连同它的前置一起挂账留独立 plan。教训 11 说"plan 是二手信息",这里的推论是:连 plan 对成本/依赖的估计也算二手,要对着现有代码复核。
17. 一个参考实现看着吓人的复杂度,开工前要**归因**:是功能本质需要的,还是它选的底座(引擎/框架/平台)连带的?两者可差一个数量级,砍掉后者只需换底座、不是硬啃。plan 24 code mode:codex 版核心引擎 ~3400 行 + sidecar ~3000 行 + `cell_actor` 一半是 observation 状态机 + 每 cell 独立 OS 线程 + `IsolateHandle` 强杀——**这些复杂度绝大多数是 V8(40MB,得移出主二进制 + 管生命周期)催生的,不是 CodeAct 本身要的**。换 rquickjs(几百 KB、进程内、原生 async future↔Promise、内建内存/超时限)直接删掉这一多半,还顺手补上 codex 缺的内存上限。归因的抓手:① 查它选这个底座的**理由**(codex 用 V8 是血统 + Cloudflare 平台本就是 V8 isolate 的红利,kloop 一个前提都不占);② 把**收益**拆到底座上——Cloudflare 自己的数字说"工具→TS API 省 81% token",证明 token 收益来自渐进披露、与 V8 无关(那半 plan 16 已有)。教训 12/16 是"量成本别照抄",这条是其推论:成本要**拆到底座**再量,换底座能让"最重的 plan"的实付复杂度掉一半。真正引擎无关的必然解(嵌套工具重入既有 gate、异步 Promise 桥、TS 声明喂模型、JSON 值边界)才照搬。
