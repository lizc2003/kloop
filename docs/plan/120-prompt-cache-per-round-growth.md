# Plan 120 — prompt cache：命中率是单轮增量的函数

> 来源：2026-09-04 一整天的 dogfood。同一个 commit `7fed2427` 被 kloop 审查了三次
> （改造前 / Plan 119 fork 版 / Plan 119 inline 版），加上 `0a79ae9a，eee68cfe`
> 那轮的三个会话，共 **2019 轮采样**的 usage 记录。
>
> 本文件替换了同编号的初稿。初稿的主线是"前缀在某处断了，去 dump 请求体做逐字节
> diff"，**那个方向是错的**，理由见第二节。

## 一、数据：命中率随单轮增量断崖下降

`total = input_tokens + cache_read_input_tokens`（kloop 的 usage 把已缓存部分从
input 里剥出来记），`delta` 是与上一轮的差：

| 单轮增量 | 轮次 | 命中率中位数 | 控制上下文 50k–150k 后 |
|---|---|---|---|
| 0–2k | 766 | 97% | 98% |
| 2k–5k | 436 | 94% | 96% |
| 5k–10k | 342 | 67% | 79% |
| 10k–20k | 323 | 48% | 45% |
| **>20k** | **152** | **14%** | **14%** |

右列排除了"上下文越大越难命中"这个混淆因素（只取 total 在 50k–150k 的 1144 轮），
相关性不变。**单轮往上下文里塞多少，直接决定下一轮能不能读到缓存。**

会话级的表现完全一致（同一个 commit、同一个 provider/模型）：

| | 工具调用 | 未缓存 input | 命中率 |
|---|---|---|---|
| 改造前（单 agent，无契约） | 199 | 6.4M | 23% |
| Plan 119 fork 版（主+子 agent） | 257 | 13.0M | 25% |
| Plan 119 inline 版 | **60** | **2.0M** | **51%** |
| codex 同 provider 同模型 | 196 | 3.7M | 70% |

inline 版命中率翻倍不是因为改了任何缓存代码——是因为工具调用从 199 降到 60，
**每轮追加的结果少了**。

## 二、初稿错在哪（连带修正 Plan 118 第四节）

初稿举的反例是：`14:34:10 total 44484 命中 44288(100%)` → `14:34:16 total 44629
(+145) 命中 0`，据此断言"增量解释不了 miss"。

**因果搞反了。** 那三轮 `task_create` 的前一轮增量是 **33146**——大增量那轮没能
写进缓存，所以随后几轮读不到本来就不存在的缓存条目。小增量轮次的 0 命中是**上一轮
大增量的后果**，不是反例。

于是两个 plan 各修正一半：

- **Plan 118 第四节**说「缓存命中率是结果不是病因，病因是每轮往上下文里塞多少」
  ——**这句是对的**，现在有 2019 轮的统计撑腰，不再只是推测。
- **Plan 120 初稿**说「增量决定 miss 的代价，决定不了 miss 的发生」——**这句是错的**，
  撤回。初稿计划的 `KLOOP_DUMP_REQUEST` + 逐字节 diff 是冲着"序列化不稳定"去的，
  而那个假设现在没有证据支持：真要断前缀，命中率不会与增量呈这么干净的单调关系。

## 三、开工时要定的（先问用户）

病因清楚了，**改法却是一个真实的取舍，不要自作主张**：

`BASE_SYSTEM` 明确要求并行批处理（"Independent tool calls in one turn run in
parallel; batch them"），而并行度正是单轮增量的来源——一轮 5–8 个 `read_file`，
每个结果 6–9k 字符，一轮就是 10–30k tokens，落进上表最差的两档。**压增量就是压
并行度，会拉长墙钟时间。**

三条路，开工时问用户选哪条（也可以都不选，只做第四条的观测）。

> **已拍板（用户，2026-09-07）：走第 2 条，外加把网关那份证据递出去，不新开工作项。**
> 第 1 条被第六、七节的数据否掉——它冲着算术那一份去，而那一份是唯一不该动的；
> 第 3 条的记录部分已经做掉（HANDOFF 107 + 本文件第六、七节）。第 2 条的理由要换：
> 不是"间接压单轮增量"（增量已被证明不是杠杆），而是**少塞进去的东西既缩小 40.9M
> 的下限，也缩小那 903 轮出问题时要重付的前缀**——为的是绝对量，不是命中率。
> 网关那份证据当时整理成一份自足的外发报告,已递给对方;它不随本仓库公开,原文在档案里。

下面三条按原文保留：

1. **限制单轮工具结果总量**：一轮内累计结果超过阈值（比如 8k tokens）后，剩下的
   调用推到下一轮。保住并行，只切分特别大的批次。需要定阈值，且要测墙钟时间的
   代价。
2. **什么都不改，靠 Plan 119 那类改动间接压**：inline 已经把 199 次调用压到 60 次、
   命中率 23%→51%。继续沿这条路（让工具一次给够、别引诱重读）也能压增量，但见效慢
   且不可控。
3. **接受现状**：把这份数据写进 HANDOFF 当已知特征，不再投入。

无论选哪条，都要先做第四条：

4. ✅ **观测**（本条已实施）：`/cost` 目前报的是 durable ledger 的累计 usage，不报
   **命中率**。加一行「cache hit / miss（本会话）」，让这个指标从"事后翻 rollout 才能算"
   变成随时可见。这是纯读，不改行为，任何一条路都需要它。

   落地形状：`/cost` 在 provider/model 分组之后多一行
   `cache hit: <read> of <prompt> prompt tokens (pct%)`，跨全部分组求和（它回答的是
   "这个会话在不在读自己的前缀"，不是"哪个模型更会命中"）。分母用新的
   `Usage::prompt_tokens()` = `input + cache_read + cache_creation`——**cache
   creation 算在分母里，因为写前缀恰恰说明这一发没读到它**；OpenAI-compat 侧
   `cache_creation` 恒为 0，于是自动退化成第一节那个 `input + cache_read` 的口径，
   与本文件的统计可比。空账本仍是 `unavailable`（不多印一行 0），全零响应印
   `(n/a)` 而不是除零。

## 四、还需要验证的

统计只证明了相关，机制还没有直接证据。真要定死，最小实验是：**同一段前缀，一次用
一轮追加 30k，一次分三轮各追加 10k，比较第二轮起的命中率**。Plan 118 拿 key 做过
类似的对照脚本（每轮 +1k，8 轮，命中 67–81%），把那套脚本的增量参数化即可，不必
新写。

如果实验证实"大增量写不进缓存"，那这是 provider/网关侧的行为，kloop 能做的只有第三
节的第 1 或第 2 条；如果实验推翻它（分三轮也不命中），才回到初稿的序列化假设，那时
再上 `KLOOP_DUMP_REQUEST`。

**不要在实验之前实施第 1 条**——阈值定错会白白牺牲并行度。

## 六、第四节的实验做了（2026-09-07）

脚本一次性的，未入库。形状：同一段 ~21k 的随机前缀，之后 30k 分两种到法——
**BIG** 一轮追加 30k，**SPLIT** 三轮各追加 10k——最后两臂都在**同一个 ~52k 前缀**上
连发 200 token 的探针轮。两臂逐轮交替发出、每个 trial 换先后手。网关 的
Responses 端点，先在 `gpt-5.5` 上跑了 5 个 trial，又在**第一节统计所用的
`gpt-5.6-sol`**（本机 2636 轮全部是它）上重跑 4 个 trial。

### 结论一：「大增量写不进缓存」——**推翻**

探针轮（追加 200 token，前缀 52k，两臂完全同形；重试过的轮次已排除）：

| 模型 | 臂 | n | 中位命中 | 逐个值 |
|---|---|---|---|---|
| `gpt-5.6-sol` | BIG | 8 | **99%** | 98, 98, 99, 99, 99, 99, 99, 99 |
| `gpt-5.6-sol` | SPLIT | 7 | **98%** | 99, 98, 98, 99, 98, 98, 0 |
| `gpt-5.5` | BIG | 10 | 93% | 89, 98, 0, 93, 90, 0, 99, 99, 88, 97 |
| `gpt-5.5` | SPLIT | 14 | 90% | 79, 0, 0, 89, 88, 99, 99, 99, 90, 89, 86, 99, 99, 99 |

**两臂没有差别。** 一轮塞进去的 30k 和三轮塞进去的 30k，事后读回来一样好；在
`gpt-5.6-sol` 上 BIG 八个探针轮**全部**命中 98–99%。第四节「如果实验证实『大增量
写不进缓存』」的前提不成立，所以第 1 条不该按那个理由做。初稿的序列化假设也不必
回去捡：前缀没有在断。

### 结论二：追加轮的命中率**精确落在算术天花板上**

`gpt-5.6-sol` 上每一个没被重试污染的追加轮（天花板 = `1 - delta/total`）：

| 轮 | 前缀 → 总量 | 天花板 | 实测 |
|---|---|---|---|
| BIG `+30k` | 21k → 52k | 42% | **40%**、**40%** |
| SPLIT `+10k` #1 | 21k → 31k | 68% | **64%**、64%、64% |
| SPLIT `+10k` #2 | 31k → 42k | 76% | **73%**、73%、73% |
| SPLIT `+10k` #3 | 42k → 52k | 81% | **80%**、80% |

BIG 那轮只有 40%，不是因为它失败了，**是因为 40% 就是它的上限**——这一轮新追加的
30k 当然读不到缓存。这是第一节那张表最直接的解释。

### 结论三：第一节那张表要拆成三份，最大的一份是算术

拿本机 84 个会话 2636 轮重算：

| 单轮增量 | n | 整条丢失 | 部分命中 | 命中且接近天花板 | 命中轮的中位命中 | 对应中位天花板 |
|---|---|---|---|---|---|---|
| 0–2k | 936 | 13% | 14% | 73% | 98% | 99% |
| 2–5k | 494 | 10% | 27% | 64% | 95% | 98% |
| 5–10k | 393 | 18% | 33% | 49% | 83% | 93% |
| 10–20k | 357 | 23% | 27% | 50% | 71% | 86% |
| >20k | 156 | 30% | 28% | 42% | **46%** | **71%** |

**命中的轮次一直贴着天花板走**（98/99、95/98、83/93、71/86、46/71），与结论二一致。
剩下的两份是：整条前缀丢失的概率随增量抬升，以及一份与增量无关、跟**前缀大小**走的
基线丢失（增量 <2k 的轮次：前缀 <20k 丢 36%、20–50k 丢 15%、50–100k 丢 9%、
>100k 丢 8%——小前缀丢得多，是因为它们多半在会话开头或压缩之后，缓存本来就是冷的）。

把前缀固定在 ≥50k、并剔除压缩后的第一轮和会话头三轮，增量那一份仍然在：

| 单轮增量 | n | 整条丢失 |
|---|---|---|
| 0–2k | 639 | 8% |
| 2–5k | 398 | 9% |
| 5–10k | 303 | 19% |
| 10–20k | 240 | 23% |
| >20k | 85 | **27%** |

**这一份实验没能复现也没能否定**：`gpt-5.6-sol` 上干净的 BIG `+30k` 只有 2 个样本，
两个都命中天花板。要定死它需要几十个 trial，本次没做。

### 结论四：第 1 条（限制单轮工具结果总量）**建议放弃**

- 它的立论前提（大增量写不进缓存）已被结论一推翻；
- 算术那一份（最大的一份）摊开也不会变小：会话总共要塞进去的 token 一个不少，
  每个 token 仍然只有第一次进上下文时是未缓存的；
- 剩下能买到的只有整条丢失概率 27%→19%，但**要付三次**：前缀 P 时期望重付从
  `0.27 × P` 变成 `3 × 0.19 × P'`，是净亏；
- 再加两次多余往返，和 `BASE_SYSTEM` 明写要求的并行批处理被打断。

### 实验本身的可信度（记下来，下次别重新踩）

- **网关的 `cached_tokens` 有假阳性。** COLD 对照（内容与 `prompt_cache_key` 都全新、
  此前从未发出）在 `gpt-5.5` 那批 5 次里有 2 次报 88% / 92% 命中。最可能是网关内部
  重试后把第二次的 usage 报了出来。绝对值要打折，但两臂受同样污染，**比较**成立；
  `gpt-5.6-sol` 那批 4 次 COLD 全部 0%，是干净的。
- **缓存按内容命中，`prompt_cache_key` 隔离不了。** 第二次跑复用了同一批随机种子，
  首轮就报 90–97% 命中——填充内容必须每次运行重新随机，否则整个实验在测上一次跑
  留下的缓存。
- 网关会返回 `502`/`504`、`upstream_error`、`gateway_concurrency_limit`，需要重试；
  重试过的轮次要单独标记并排除（重试本身会制造命中）。同一臂内 `input_tokens` 必须
  单调，网关过载时出现过非单调（误报），那批数据整个作废。
- 三次跑合计 13 个 trial，花费约 `$1.2`。

## 七、追问「缓存到底有没有问题」——有，而且不在算术那一份上

第六节回答的是"那条断崖是怎么来的"，回答不了"钱花得对不对"。把本机 2636 轮实付的
未缓存 input 拆开（下限 = 每轮**新追加**的 token，压缩那轮的新前缀整条算下限）：

| | 轮次 | 未缓存 input | 占超支 |
|---|---|---|---|
| 下限（怎么都得付） | — | 40.9M | — |
| 健康轮（贴着天花板） | 1421 | 1.5M | 2% |
| **命中了但远低于天花板** | **534** | **42.1M** | **55%** |
| **整条前缀丢光** | **369** | **33.5M** | **43%** |
| 实付合计 | 2636 | 118.0M | — |

**超支 77.1M，是下限的 1.9 倍；98% 集中在那 903 轮不健康的轮次上。** 命中率曲线的
形状主要是算术，但花掉的钱主要不是。

### 那 534 轮命中了什么

拿 `cache_read` 去对更早各轮的 prompt 长度，232 轮能对上**2–30 轮之前**那一轮
（"1 轮之前"只有 1 例，因为对上 1 轮之前就是天花板、已被划进健康轮）。例：

```
20260831-131759.jsonl round 11: prompt 32956, cache_read 13824 == round 3 的 prompt (13765)
20260902-101948.jsonl round  7: prompt 17286, cache_read 10752 == round 5 的 prompt (10989)
```

即**网关的缓存条目落后好几轮**：不是每一轮的前缀都被写进去，落后期间追加的一切
下一轮全部重付。`cache_read` 一律是 128 的整数倍（7680=60×128、13824=108×128），
块大小 128。第六节的实验里看到同一形状——前缀 42k 的那轮只命中 20224，正好是最初
那段 21k 的 base。余下 302 轮在 30 轮内对不上任何一轮。

### 对改法的影响

这三份里 kloop 能碰的只有下限那一份（少往上下文里塞东西），而它只占超支的 2% 之外
的那个"下限"本身。**超支的 98% 是网关侧的写入/保留行为，kloop 改不了**——这也再次
说明第 1 条不该做：它冲着算术那一份去，而那一份恰恰是唯一不该动的。
