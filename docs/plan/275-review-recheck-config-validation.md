## 需要纠正的前提

plan 273、274 的脚本只复用了本机配置的端点、鉴权和模型；输出上限、high effort 和
120 秒总截止由实验另设，不能称为正常 kloop 的运行条件。当前配置为 Responses 模型
`deepseek-v4.1-flash-1017`、xhigh，没有 provider 或 model 层的输出上限声明；route
回退值为 65,536。正常 provider 的开流、流空闲、流读取总截止分别为 300、900、1,800 秒。

## 采样前冻结的协议

- 使用现有 kloop 二进制和临时配置，先通过本机 HTTP/SSE 接收端核对正常启动实际发送
  的输出上限与 effort。临时配置只把当前 provider 的端点指向本机，不改真实配置。
- 原四份冻结候选、证据、提示与真值逐字节复用。每组 3 次，共 12 次，同时最多两组；
  无工具、无历史、无初审裁决和答案标签，不重试、不补样，不续写未完成结果。
- 真实请求沿用当前配置的端点、鉴权、模型和 xhigh；输出预算使用本机启动探针核实的
  65,536。开流等待 300 秒、读取空闲 900 秒，父进程提供 1,800 秒整次请求硬截止。
  该整次截止比原生在开流后启动读取总计时略严，不能称为相同传输实现。
  记录超过旧 120 秒截止才完成的调用，不再用实验短截止判断正常预算是否够用。
- 复核仍为独立 Responses 请求，不经过完整 agent 工具循环；本机启动探针验证配置到
  实际请求的边界，不能把独立复核实验说成 `/code-review` 端到端验证。
- 提示、真值和代码不因输出改变；全部已交付裁决人工核对，错误排除、误报、unresolved、
  输出截断、传输失败、超时分别统计。记录 token、耗时和实际请求参数，缺 usage 不当零。
- 这轮同时纠正输出上限、effort 和时间限制，不是单变量对照。旧组是历史数据，原留出
  材料本轮已知；不能据此宣称单独提高输出上限造成全部收益，或生产召回、成本已改善。
- 原始请求、响应、配置副本只留本机临时目录；配置副本用 0600 权限并在探针结束后删除。
  仓库只记录方法和汇总，不写端点、凭据或原始捕获。

独立缺陷共五个、独立对照四个，不把三次重复当作更多独立样本。

R3 三次均交付完整、引用可校验的裁决：

| 次数 | 用时 | 输出 token | 其中推理 token | 人工验收 |
| --- | ---: | ---: | ---: | --- |
| 1 | 183.000 秒 | 25,320 | 24,886 | HOME 丢失造成正常 home 路径误拒，成立；对照正确排除 |
| 2 | 171.379 秒 | 23,504 | 23,149 | 同上，成立；对照正确排除 |
| 3 | 227.501 秒 | 30,311 | 29,896 | 确认标签对，但触发例子不成立；对照正确排除 |

三次输出都超过 16,384，用时都超过 120 秒，原实验的任一限制均容不下这些完整输出。
第 3 次声称 `bash -e -c 'cat rel'` 的普通相对路径会被判未知并拒绝。目标版本的实际
消费方中，`cwd_unknown` 只把读取位置改为只信绝对路径；`ReadUnlocated` 影响 `.kloop`
的路径豁免，不会把任意 `rel` 变成含未知片段的参数，也不会直接返回 `Unresolved`。
因此这条不能作为可直接报告的缺陷论证，不能仅凭 confirmed 与真值相同算作正确救回。
真实缺陷仍是 HOME 被丢弃后的 home 路径误拒，其他两次已经给出有效触发条件。

完整组 12 次耗时 35.0–227.5 秒，中位 62.5 秒，各请求时长合计 1,055.6 秒；有并发，
合计不是整批墙钟。12 次均有 usage：总输入 67,148 token（含缓存），输出 137,394，
其中推理 132,711。五次输出超过 8,192，三次超过 16,384，三次完成晚于 120 秒；
无输出截断、超时、SSE 解析或裁决格式失败。父进程 1,800 秒截止未被触及。

首批六次失败无可用 usage，各次时长合计 180.1 秒。两批共 18 次请求尝试，取得 12 次
完整响应；不能只报告“总共 12 次且全部成功”，也不能把首批未取得裁决记成正确排除。
总消耗应为完整组已知用量加首批未知量，不能宣称本轮更省 token。

## 结论与取舍

- 正常 kloop 的上限是 65,536，实验曾人为压到 8,192/16,384，再以 120 秒提前截止。
  完整组没有复现这些预算失败，R3 的三次实际输出和完成时间也都超过旧限制；先前用
  受限实验断言正常条件下“复核无法可靠交付”的前提不成立，应纠正而非延续。
- 这轮同时改变输出上限、effort、时间限制和执行环境，不能将所有差异单独归因于
  token 上限。首批传输失败的来源未确定；完整组成功不能抹去这些失败。
- 交付与正确性仍是两道验收。R3 已能交付，却有一次把不成立的触发条件写进确认理由；
  机械标签满分会掩盖它。正确候选、有效 JSON 和有效坐标都不等于有效缺陷论证。
- 结果支持继续研究独立复核，正常采样上限无需从 8,192 往上改，因为它原本就更大。
  本次不改产品配置、benchmark 的实验默认值或 `/code-review` 流程；自动准备候选与
  证据的成本、新样本上的端到端召回、无人工验收时的效果仍需另行验证。
