# Plan 278 ✅ — 结构化裁决与同输入前后比较

> 2026-11-10。用户要求继续优化裁决交付与错误排除。

## 范围

仅扩展外层 benchmark 的显式 `--decision-contract`；共享循环、生产 `/code-review`
及原实验入口默认行为不变。通过专用提交函数交付裁决，每个候选是必填对象属性，
每项明确 verdict、severity、reason、comparison、basis、evidence、missing。
动态 schema 只接受本候选已经授权的来源编号与行范围；预算最后一轮只允许提交，
不再查询源码。提交不计入只读查询次数；首轮不设额外格式重试，后补的显式单次修复
见下。禁止静默补字段或降级正文。

确认与排除都必须列出同一具体输入、修改前行为、修改后行为；排除根据区分失败被
否定、同一故障原已存在、变化无害。“更保守”“符合新文档”本身不算行为证明。
机器只能校验结构、字段、来源与声明的依据，事实是否成立仍人工验收。

## 验证协议（请求前冻结）

- 局部回归覆盖必填/额外/重复属性、候选完整性、跨候选引用与行范围、前后比较、
  来源补查后的 schema 更新、最终提交选择、混合提交/查询拒绝、失败不重试及空候选。
- 本机真实二进制重新捕获采样，沿用正常模型、effort、输出与传输预算。
- 一次极小真实兼容请求核对强制函数提交；不通过则保留失败并停止依赖此能力的请求。
- worktree 和 R3 旧材料各一对开发回归，旧补查模式对照新裁决模式，各一次。
- 另冻结一份未用于先前实验的合成双版本材料，包含两条功能回归、两条不变行为。
  先用确定性输入核对真值，真值/探针不进模型仓库，再做同样一对。不称真实留出提交，
  不把合成易例外推成生产召回率。
- 三对都允许相同补查能力：最多 8 次请求（包括提交）、64 次只读查询、额外
  160,000 字符、200 行/次读取、12 处/次搜索。新组增加提交函数与前后比较要求；
  新组关闭平行调用并强制每轮选择查询或提交函数。这是组合开发改动，不分离宣称
  schema、提示或工具选择各自的效果。
- 冻结所有材料、提示、脚本与协议后运行完整六次，不根据结果挑样、改问题或重跑。
  所有失败和成本保留，分别报告格式/引用交付、具体论证与真缺陷保留。

### 决定

保留三个显式实验选项，均不默认接入生产审查。本轮证明前后行为字段有助于暴露错误
排除，新组也找到了 R3 的有效触发；未证明稳定交付、端到端减少漏报或更省成本。
强制函数和 strict 仍出现漏候选、非法参数、重复调用，单次反馈未解决。
下一步应先核对当前接口中模型生成与工具参数转换的边界，确认哪种交付方式真正能
保证可解析，再扩大审查实验；不继续靠追加提示、扩大预算或挑选已通过响应推高分数。

## 首轮后补充：单次显式格式修复

首轮新组三次分别为：worktree 交付通过，R3 找到真缺陷但漏交对照候选，合成材料
提交参数不是有效 JSON。强制函数与 strict 不代表当前网关会保证参数语法或 schema。
原六次全部保留，不回改为成功。增加默认关闭的 `--repair-decision`，只对一次独立
提交函数的本地校验失败反馈错误，额外允许一次完整重交；不提供答案、不静默补字段、
不放宽校验。修复请求只允许提交，不查源码；第二次失败、传输失败或混合查询/提交
均停止。请求总上限由 8 明确增至 9，额外成本独立记入元数据。

局部回归后，先冻结修订脚本与反馈正文，再分别从原 R3/合成失败的最终请求历史续接
一次真实格式修复；不重跑调查，不用通过的 worktree 凑成功率。原尝试仍失败，续接
单列为失败后的开发验证，组合成本包含原失败；人工核对新裁决，不能把合法格式当召回。
