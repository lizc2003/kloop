# Plan 151 — 模型在原地打转,没有人发现

> 来源:2026-09-15,借鉴项目调研后按 macOS-only 前提重排的第三条。两件都来自
> `refs/deepseek-harness` 的 `packages/guard/*`(见 `refs/README.md` 2026-09-15 节),
> 是设计语义而非代码——dsh 是 TS,这里按规格重实现。

## 一、两个洞,都在同一个位置

`dispatch_tools`(`core/src/tools/mod.rs:697`)→ `execute_tool`(`:1247`)这条路上:

**洞一:没有人数过同一个工具被用同样的参数调了几次。** 全仓 grep `repeat` 只命中字符串
`"x".repeat(201)` 和文档里的 "repeating it verbatim",没有任何循环检测。模型卡在
同一个 `grep` 上换着姿势调五次、或者反复 `read_file` 同一个文件,现在没有任何反馈——
它看不到自己在打转,只看到又一个正常的工具结果。

**洞二:工具执行没有统一超时。** `bash` 自己有 `timeout_ms`(`tools/bash.rs:217`,默认
60s),`hooks` 有 `DEFAULT_TIMEOUT_MS`(10s)。但 `execute_tool` 是裸的 async,一个
外部 `ToolSource`(MCP server、程序源)挂住就是无限期挂住。取消机制是有的
(`ctx.cancel`),缺的是"到点自动取消,并给模型一个说得清的 timeout 错误"。

## 二、做什么

### 一、重复调用提醒(advisory,绝不阻断)

- 按 `(tool_name, canonical(args))` 计数。args 要规范化(JSON key 排序)后取哈希,
  别存原文——`read_file` 的参数可能很大。
- 命中第 3、5、8 次时,在该次工具结果后追加一条提醒,请模型先看上一次的结果、
  换个做法或收尾。**只在这三个点提醒**,不是每次都提醒。
- **按 agent 分别计数**:子 agent 和 root 各算各的(`agent_type.rs` / `LocalAgentId` 已有
  身份),否则并行子 agent 会互相污染计数。
- **新的用户消息清零**。用户换了话题,之前的重复不该继续累积。
- 永不阻断、永不延迟一次合法的重复调用。`ls` 连调十次可能完全正当。

### 二、每工具 cooperative 超时

- 每个工具自带上限(不是全局一个数):`bash` 沿用它已有的 `timeout_ms` 不动;
  只读的 `grep`/`glob`/`read_file` 给一个短上限;外部 `ToolSource` 给一个较长的。
- 到点触发 `ctx.cancel` 的子 token,等取消 settle 之后再给模型 timeout 错误——
  **不是**到点就撕掉 future,那会留下半跑的进程和写了一半的文件。
- 错误信息要诚实:**说明工具可能仍在后台跑**。一个不理会取消的工具,这套机制停不住它,
  dsh 自己也这么写在文档里。不要在措辞上假装它被杀死了。

## 三、坑

- **计数放哪儿**。放 `ToolCtx` 里会随每轮重建;应该挂在会话级(`agent` 侧)并通过 ctx 借用。
  放错地方会让提醒永远触发不了或者永远触发。
- **提醒算不算 model-visible**。它进模型上下文,所以必须能被 rollout 重放出来
  (HANDOFF 的 append-only 硬规则)。不能是只在 UI 上显示的东西。
- **别和 compaction 打架**。提醒是短文本,但压缩后重放要保持一致;跟着工具结果走,
  不要单独成一条 history 条目。
- **超时不能改变并发批的语义**。`dispatch_tools` 会把只读调用批量并发
  (`is_concurrency_safe`),一个超时不该让整批失败。
- `bash` 的 `timeout_ms` 是模型可以传的参数;新加的统一超时**不要覆盖模型的显式选择**。

## 四、开工时问用户(先问,再动手)

**这两件是一个 plan 还是两个提交?**

它们唯一的共同点是都落在 `execute_tool` 附近,语义上毫无关系(一个是对话质量,一个是
资源安全)。按仓库习惯(一个 plan 一个会话任务、一次 commit)更像是**一个 plan 两次提交**。
开工时确认一下要不要拆成 151/151b,免得一次 commit 里混两件事。

## 五、非目标

- **不做 dsh 的其余 guard**。那边还有别的策略包,本 plan 只要这两件。
- **不引入工具级重试**。超时后重试是另一个决定,`provider` 侧已有重试语义,别在这里再来一套。
- **不做"检测到打转就自动收尾"**。提醒是给模型的信息,不是控制流。真要自动终止是另一个设计。
- 不改 `is_concurrency_safe` 的批量规则。

## 六、验收

### 重复调用提醒

1. **边界精确**:同一 `(tool, args)` 连调 8 次,提醒恰好出现在第 3、5、8 次之后,
   第 4、6、7 次**没有**提醒。整对象断言工具结果序列,别只断言"包含提醒"。
2. 参数不同就不算重复:`grep{pattern:"a"}` 与 `grep{pattern:"b"}` 交替调 8 次,零提醒。
   JSON key 顺序不同要算同一次(规范化生效)。
3. **按 agent 隔离**:root 调 3 次、子 agent 调 2 次同一工具同一参数,只有 root 收到提醒。
4. **用户消息清零**:调 2 次 → 新用户消息 → 再调 2 次,零提醒。
5. **永不阻断**:第 8 次调用本身仍然正常执行并返回结果,提醒是附加的。
6. 提醒进了 rollout,fork/resume 后重放出来的历史与原会话一致。

### 每工具超时

7. 一个故意挂住的工具到点后:模型收到 timeout 错误,且错误文本**明说该工具可能仍在后台跑**。
8. **取消先 settle**:断言 cancel token 已触发且工具的清理路径跑完,再有错误返回——
   不是到点就丢掉 future。
9. **并发批不连坐**:一批并发只读调用里一个超时,其余的结果正常返回(`is_concurrency_safe`
   的批量语义不变)。
10. **不覆盖显式选择**:`bash` 带 `timeout_ms` 参数时,用模型给的值,不是新的统一上限。

11. 仓库完成标准照旧(fmt / clippy -D warnings / test,各自取退出码)。如按第四节拆成
    两次提交,两次各自全绿。
