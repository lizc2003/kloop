## 二、第一阶段：基础行编辑与按词编辑

这一阶段是 plan 211 的实施范围，可独立验收与提交：

- **Ctrl+A / Ctrl+E**：到硬逻辑行首 / 行尾，与现有 Home/End 同语义，不按视觉折行定位。
- **Ctrl+B / Ctrl+F**：左 / 右一个字素，与现有 ←/→ 同语义。
- **Alt+← / Alt+→、Ctrl+← / Ctrl+→、Alt+B / Alt+F**：按词左 / 右移动。
- **Ctrl+W、Alt+Backspace、可辨认的 Ctrl+Backspace**：删除前一个词。
- **Alt+D / Alt+Delete**：删除后一个词。
- **Ctrl+U**：删除到硬行首；已在行首则删除前面的 `\n`。
- **Ctrl+K**：删除到硬行尾；已在行尾则删除后面的 `\n`。

**本阶段的删除不保存剪切内容，不新增 Ctrl+Y 或 Alt+Y，也没有撤销。** 不把删除描述成已经
具备恢复能力的 kill/yank；这些边界必须同步写进第一阶段落地后的 DESIGN。暂缓项不需要
Fragment、ring、yank 区间、轮转索引或预留字段。

### 2.1 保留的键与分发顺序

- Ctrl+C 仍为两击退出；Ctrl+D 仍禁用，不改成 readline 的删字符或退出。
- Ctrl+R 仍为空闲时 rewind；Ctrl+V/Alt+V 仍为图片粘贴；Ctrl+T、Ctrl+J、Shift+Tab、Esc
  保持现有行为。待答交互、provider picker、rewind picker 仍优先捕获输入。
- 换行仍先于补全接受处理；补全菜单仍先吃 ↑/↓/Ctrl+P/N/Tab/Enter/Esc。
  其他编辑键修改 composer 后，必须走 `App::after_edit` 重过滤、更新或关闭菜单。
- `App` 只映射键与路由；词边界、范围删除与光标状态放在 `Composer`。可用穷尽的
  `ComposerAction` 与纯映射函数集中列举新键，方便表驱动测试，不借机重写其他面板分发。
- 映射区分 Ctrl、Alt 和 Ctrl+Alt，不能只用 `contains(CONTROL)` 把 AltGr 或组合修饰键误当
  Ctrl+B/F 等新动作；未绑定的 Meta 键继续无操作，不插入字符。

### 2.2 终端编码

- Alt+Backspace 的传统序列 `ESC DEL` 需要经过真实解析验证；不能只构造带 ALT 的 KeyEvent。
- Ctrl+Backspace 只在终端能明确区分时绑定。**不把 Ctrl+H 当作删词别名**，避免把普通退格
  误变成删词；不可辨认的终端保持现状，不宣称所有终端都能使用这个组合。
- `rust/crates/tui/src/lib.rs:658` 在 Unix 请求 `DISAMBIGUATE_ESCAPE_CODES`，这是 best effort，
  终端、tmux 或 SSH 是否透传 CSI-u 另有边界。Meta 和增强编码分别测试，不凭请求了模式
  就断言所有终端会发相同键码。

## 三、第一阶段的文档与粘贴原子约束

### 3.1 词边界

开工先按第四节问清“词”的规则，再定落点序列。原稿推荐的字符类方案是：

- 空白、词字符（字母数字或 `_`）、其余标点三类；向左先跳空白，再跳一段同类，向右对称。
- `\n` 按空白处理，按词移动可以跨硬行。Ctrl+U/K 的行内删除不使用这个跨行词规则。
- 必须按完整字素迭代，不能用 char 下标当字素边界；组合字符、ZWJ emoji 都不能拆开。
- **paste atom 优先于字符分类。** 每一步扫描都先识别原子，不把标签里的空格、标点或
  首行预览当成可编辑的词；相邻原子一次越过整体，原子两侧的文本仍按选定词规则处理。

### 3.2 范围删除不能误展开粘贴

`ComposerDocument::replace`（`composer.rs:120`）会通过 `materialize_intersections`
（`composer.rs:150`）先展开相交原子。它服务于已有的任意范围编辑，**不能直接拿来实现
“删除一整个原子”的新动作**，更不能在展开后的载荷上重新算词边界。

新增词/行范围删除应保证：

- 相交的 paste atom 整体删除，端点对齐完整原子范围；标签与载荷一起移除，不把载荷摊进 display。
- 剩余原子的区间、标签和内容仍一致；删除后重新保证光标的字素边界与显示布局，不遗留
  指向旧区间的状态。既有需要物化的 `replace_range` 语义不改。
- 不只测光标刚好邻接原子的路径。当前 `ComposerLayout::offset_at_column`
  （`composer.rs:399`）只看显示文本与列，↑/↓（`composer.rs:581`）没有查原子范围；不能把
  左右移动的原子保护当成所有入口的保证。新词动作若从标签内部开始，左/右移动应落到
  相应原子边界，范围删除也必须覆盖完整原子。补这个入口的回归，不顺带重写纵向布局。
- 空文档、文件两端与空删除范围均为无操作；删除不影响图片附件、输入历史或粘贴编号高水位。

## 四、第一阶段开工先问用户

**“词”按什么切？** 一次只问这一点，不把推荐写成用户已经决定。

- **推荐字符类**：字母数字下划线一段、标点一段、空白跳过。汉字属于字母数字类，连续中文
  到空白或标点为止算一段，所以 Ctrl+W 可能删掉一整段中文，用户必须知道这个行为。
- UAX#29 词边界：已有 `unicode-segmentation` 依赖可用，但它不是中文词典分词；中文的效果
  与字符类不同，不能承诺像自然语言分词一样删掉一个中文词。选它时用实际落点样例确认，
  不凭依赖名称决定语义。

两个方案都必须保留字素安全、原子整体性和跨行规则；实现前记录用户答案与独立的期望序列。

## 五、第一阶段测试与验收

### 5.1 Composer 单测

优先整对象断言 `(text(), cursor())`；带原子时同时检查完整 atoms 的区间、标签与内容。

- `"foo  bar.baz"` 在各位置的词移动/删除序列；空串、首尾、连续空白、跨 `\n`、中文与标点。
  期望由第四节确定的规则独立写出，不从被测 helper 推导。
- 组合字符、ZWJ emoji、CJK 的每个落点都在字素边界；删除后两侧字素重新结合的情形也要测。
- 含一个及多个 paste atom 的移动、删词、Ctrl+U/K；扫描到标签内部空格不能停下，删除后
  payload 不在 display，剩余原子区间正确；提交展开后的文本与预期完全一致。
- 从视觉行导航落在原子标签内部，再调用新词动作/范围删除，验证完整性。
- Ctrl+U/K 在硬行首/尾删除相邻换行；视觉折行不当作硬行；空范围不改变状态。
- 保持现有输入历史、草稿、图片附件、粘贴编号高水位与普通退格/前删语义。

### 5.2 App 键位与菜单单测

- 表驱动断言整个键位映射，包含普通、Ctrl、Alt、Shift 和 Ctrl+Alt 情形；不接受未声明的
  修饰组合误触新动作。Alt+B/F 执行移动，未绑定 Alt+Q 不插字符。
- 保留键回归：Ctrl+R/V/Alt+V/D/C、换行、Shift+Tab、Esc 与面板/菜单优先级。
- 补全菜单打开时删词、移动、删除行内文本后正确重过滤或关闭；晚到的文件搜索结果不能
  用旧光标范围覆盖新文本。

### 5.3 真实 PTY

在 `rust/crates/cli/tests/tui_pty.rs` 的现有 harness 上扩展；参考
`unicode_input_round_trips_through_real_binary_editing`（`tui_pty.rs:429`）。

- 用原始字节发送基础 Ctrl 键、Meta 词移动/Alt+Backspace，以及明确可辨的增强方向/删除编码。
  声明各用例实际覆盖的键码，不把构造 KeyEvent 的单测当作终端已验证。
- 经编辑后提交，断言本地假 provider 实际收到的完整用户文本；覆盖 Unicode 与大粘贴原子，
  不能只看屏幕上的标签或光标。
- 持续读取 PTY、回应 CPR；整屏断言使用稳定帧。测试只用本地假 provider，无真实 API/key。

这类功能是确定性的键盘编辑契约，**不需要真实模型 A/B**。新动作单测 + 真实字节到提交文本
的 PTY 证据承担验收，真实终端/平台没有执行的部分如实声明，不借 macOS 结果声称 Windows 已跑。

## 六、后续阶段备忘：可靠撤销（另立 plan，不随第一阶段实施）

撤销值得做，但下面只是后续任务的边界，**不是已经定稿的实现方案**。

### 6.1 状态与生命周期

- 撤销应恢复文档（含原子及载荷）、光标和图片附件；撤销状态不回退 `next_paste_id`，不把
  已提交消息的输入历史改掉。恢复后结束历史浏览，清除旧的视觉列目标与动作合并状态。
- 提交与 `submit_text` 清空本次草稿的撤销历史，不允许撤销出已经发送的消息；撤销历史
  浏览应能回到浏览前的草稿。粘贴、补全接受、附件变更和清空都要有明确的恢复边界。
- 只移动光标和无效果的操作不压快照。普通输入如何合并、空白/退格如何分组，先用独立
  的动作序列确定体验；原稿的 fish 式合并只是参考，本次未选定。

### 6.2 内存设计必须重做

**撤回“完整 clone 最多 100 个快照即可”的方案。** 当前 `PasteAtom.content` 是 String
（`composer.rs:44`），图片附件持有 ContentBlock（`composer.rs:306`），其 base64 数据也是
String（`rust/crates/protocol/src/lib.rs:407`）。直接 clone 会在编辑普通文字时反复复制大载荷，
限制快照条数不能代替总字节成本控制。

撤销阶段动手前必须明确并写进它自己的 plan：

- 大粘贴和图片载荷如何共享不可变内容，避免每次按键深拷贝；共享不能引入快照间可变别名，
  也不为本地输入框需求改 provider wire 或全局 ContentBlock 语义。
- 如何核算撤销历史保留的文本、共享载荷、元数据，何时释放不再可达的载荷；共享数据不能
  每份重复扣费，也不能因为共享而漏掉仍被快照保留的内存。
- 快照数量与总字节预算、单个状态超过预算时的可观察行为。不能通过截断用户文本或图片
  来满足预算，也不能只证明“最多 N 条”就声称内存已受控。

本次不预选具体共享类型、预算数字或驱逐策略；这些是撤销阶段的设计输入，不留给代码临时猜。

### 6.3 撤销阶段开工再问

一次一个点，记录定稿后再实现；本次用户只同意修订计划，没有替这些问题拍板。

1. 撤销键：推荐 Ctrl+_，是否另加 Ctrl+Z 仍待用户定。Ctrl+Z 与终端挂起习惯有关。
   原稿列过 Ctrl+7、Ctrl+-、Ctrl+Shift+_ 等编码；届时核对实际 crossterm 版本，并用
   `0x1F` 与 CSI-u 原始字节测试，不只测试构造出的 KeyEvent，也不提前占用这些键。
2. 两击 Esc 清空能否撤销：推荐能，连同图片附件恢复，但不能把两击确认改掉。
3. 用实际载荷规模给出内存方案，再与用户定预算与超预算行为；输入合并粒度在方案中说明。

### 6.4 撤销阶段验收

- 状态恢复、输入分组、删除/粘贴/补全/附件变更、输入历史浏览、空栈与提交后的边界。
- 粘贴撤销后再次粘贴编号递增；如用户选择可恢复清空，验证文本与图片完整恢复。
- 大文本和图片连做多次小编辑，不反复深拷贝载荷；预算与驱逐可观测，共享载荷最后引用
  释放后可回收；不能只看条数或只测一个小字符串。
- 传统与增强撤销编码的真实 PTY 回归；未改变 Ctrl+Z 行为时保留其现状。
