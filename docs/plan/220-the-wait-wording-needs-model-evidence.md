# Plan 220 — 等待措辞的收益，要由模型的工具选择证明

## 复审结论

P2 成立：单元测试只证明了两件事——工具说明包含指定文案、回执示例可以调用且工具会提前返回。
它们都没有证明模型从固定 `sleep` 改选 `bash_output`。在真实 A/B 之前，只能说调用契约已补齐，
不能说措辞有效或死等频率已下降。这正是 HANDOFF 教训 213 的适用范围。

两项 P3 同步处理：DESIGN 的这条 bullet 恢复为英文，与相邻说明统一；测试的最长等待值改由
`BLOCK_TIMEOUT_MAX_MS` 推导。

## 出事样本

已在本机原始会话中定位到：用户原话为「同意，以及按照这个结果，做最合理的代码修复」。
模型修复代码、启动三轮真实验证之后，在收到后台启动回执的下一步调用了 `sleep 170`，随后又
调用 `sleep 110`。路由为 Responses，模型 `deepseek-v4.1-flash`，effort 为 `xhigh`。

**不能只重发这句用户原话，也不能另写一句“请等后台任务”代替。** 触发点在长会话后段，
必须保留出事位置之前的原始上下文，并在后台启动回执之后、第一条 `sleep` 之前截断。
原始会话、请求与响应只留在本机临时目录，不提交原始捕获、凭据或个人路径。

## 预先固定的对照

- A：旧工具说明与旧启动回执；B：`4d49ba0` 的新工具说明与新启动回执。
- 两个二进制使用同一份代码与相同构建标识，只替换这三处生产文案；测试与文档差异不进入运行时。
- 使用同一模型、代理、effort、输出上限、工具清单及原始上下文；每次独立重放，交替 A/B 与 B/A。
- 先核对两个发出请求的差异只来自工具说明和该次启动回执。不得向 B 额外追加“不要 sleep”等提示。
- 每组预定 30 个样本，不根据中途结果增减；技术失败单列，保留分母，不按有利结果补算成功。
- 只观察出事位置后的第一条模型回复。工具执行前拦住所有调用，不执行真实构建、额外 API 轮次或
  固定 `sleep`，也不给模型一次拒绝后的反馈再让它改选。

## 计数与结论

主指标按独立重放计数：第一条工具调用分别为 `bash_output`、带固定 `sleep` 的 `bash`、其他工具、
无工具调用或技术失败。另记该回复内是否出现任何固定 `sleep`，避免批调用把它藏到第二条。
记录 `bash_output` 是否指向正确 ID、是否阻塞；只有指定命令的阻塞等待才算本次目标行为。

报告两组完整计数和比例；若给 Fisher 检验或区间，作为补充，不能把有限样本中的零次当成保证。
若旧措辞重放不出问题，就明确说明本轮没有证明收益；若新措辞仍失败，保留失败样本并据此调整，
不通过改掉出事上下文或给新组额外暗示来“修好”实验。

## 实测方法（2026-10-09）

从同一份 `4d49ba0` 源码导出临时副本，加入两组共用的单次采样入口。
B 保持生产文案；A 只把 `bash_def`、`bash_output_def` 与启动回执的生产文案恢复到
`33fb49f`。分别构建两个 dev 二进制，构建标识相同；没有修改等待实现或增加系统提示。
两组都从用户指定配置复制凭据，每个样本使用独立临时 HOME 与会话副本。

截断原始会话后，用原生 `History::resume` 恢复历史与已冻结的三条请求裁剪 stub，
保留 provider 对历史 reasoning 的原生投影；原始用户消息不改写，也不追加新的用户指令。
B 仅替换最后一条后台启动回执，并核对它与生产 `format!` 实际渲染的字符串相同。
系统提示使用本次原生启动生成的一份固定内容，两组共享；这是原始消息上下文的重放，
没有恢复事发当天未落盘的系统环境快照。

共用采样入口直接调用原生 `Provider::stream_attempt`，收完首条回复即结束。
没有进入工具执行器，因此不会执行模型生成的 `sleep`、构建或下游 API 命令，也没有拒绝后的
第二次机会。这验证的是触发点的模型工具选择，不是完整 CLI 后续会话或真实作业的完成时间。

请求为 Responses / `deepseek-v4.1-flash` / `xhigh`，输出上限 65,536 tokens，
286 条恢复消息在 wire 上展开为 559 个 input items，工具清单共 28 个。
预采样导出请求，核对全部 JSON 字段后，差异只有四处：`bash` 描述、`bash_output` 描述、
后者的 `timeout_ms` 字段描述、最后一个 tool result 中的启动回执。
正式 60 个请求也逐个核对，全部与各自组的预采样请求相同。

每组按预定数量跑 30 次，以 A/B、B/A 交替顺序发起，最多并发 4 个独立样本。
没有按中途结果调整输入、样本数或补算成功。原始请求、回复、每轮工具调用和汇总均保留在
本机私有临时实验目录；不提交原始捕获、凭据或个人路径。
采样结束后清除了全部临时凭据副本，用户的原始配置没有改动。

## 完整结果

| 观察项 | A：旧文案（30 次） | B：新文案（30 次） |
|---|---:|---:|
| 第一条工具调用为正确 ID 的阻塞 `bash_output` | 0（0%） | 3（10%） |
| 第一条工具调用为带固定 `sleep` 的 `bash` | 30（100%） | 27（90%） |
| 第一条工具调用为其他动作 | 0 | 0 |
| 没有工具调用 | 0 | 0 |
| 技术失败 | 0 | 0 |
| 整条回复出现固定 `sleep` 工具调用 | 30（100%） | 27（90%） |

B 的三次正确等待都使用 `bg-10`、`block=true`，上限分别为 600,000、420,000、
600,000 ms。其余 B 样本仍直接写固定 `sleep`，时长为 170–240 秒。
A 的固定等待为 150–230 秒。没有“先选 `bash_output`，同条回复里又偷偷 `sleep`”的样本。

正确阻塞等待的比例从 0/30 到 3/30，Fisher 双侧检验 `p≈0.2373`。
这批样本不足以确认有稳定改善；也不能把未达到显著差异解读为两种文案效果必然相同。
可以明确的是：**新文案在原始出事上下文中仍有 90% 的首轮调用使用固定 `sleep`，
所以 `4d49ba0` 不能算解决了用户报告的死等问题。**

以上是完成预定 60 次采样后的基线结论，不能把其中的 3 次成功写成“已修复”。

## 继续修复：把等待约束放进 harness 消息

用户看到上述结果后要求「要想办法解决啊」。系统提示本来就把工具输出视为数据；
继续向启动回执堆指令并不能保证模型采纳。新方案保留原工具说明和回执，在轮次边界把
当前活跃后台 Bash 的 ID 与等待规则作为独立 `Injected::Harness` 消息追加到历史尾部。
它与其他 harness 提醒使用同样的 `<system-reminder>` 形状，不混进 tool result，
也不改动系统提示的缓存前缀。

提醒明确覆盖“作业把结果写到另一个日志”这一场景：先用该 ID 的阻塞 `bash_output`
等待结束，再读实际日志；仍可继续无依赖工作。ID 清单来自原生注册表，只列活跃作业，
顺序稳定；同一清单不重复追加，作业结束后不产生新提醒。压缩或 rebase 后清空去重状态，
下一轮按活跃注册表重新注入。没有拦截或改写合法脚本中的 `sleep`。

先做了独立的 10 次探索采样：仅在 B 请求尾部增加这条 harness 提醒，9 次首选正确阻塞的
`bash_output`，1 次直接读取当前日志，固定 `sleep` 为 0/10，无技术失败。
这 10 次只用于开发，不合并进正式结果。

正式确认预先固定为 **30 次 B（`4d49ba0`）+ 30 次 C（新增原生 harness 提醒）**，
重新采样两组，交替 B/C 与 C/B，最大并发仍为 4。原始截断位置、系统提示、模型、代理、
输出上限、工具清单与原生请求投影保持一致；先核对请求差异只有新增的最后一条提醒。
正式结果不因探索或中途观察而增减样本，不按有利结果补算成功。

### 独立确认结果

C 使用修复后的原生格式化函数与历史记录入口生成提醒；重放入口以事发时的活跃 ID
`bg-10` 作为状态夹具，没有重新执行原始构建或三轮下游 API 命令。实际 agent 循环从注册表
取 ID、在 tool result 后独立注入、去重、尊重工具 allowlist、压缩后恢复及结束后停止提醒，
由 mock provider 加真实后台进程的集成测试覆盖。单测不承担证明模型会采纳文案的职责。

确认请求的唯一差异是 C 尾部多出的这条提醒，input items 从 559 到 560；
正式 60 个请求逐一核对，全部与各自预采样请求完全相同。

| 观察项 | B：`4d49ba0`（新采 30 次） | C：原生 harness 提醒（30 次） |
|---|---:|---:|
| 第一条调用为正确 ID 的阻塞 `bash_output` | 3（10%） | 27（90%） |
| 第一条调用为正确 ID 的非阻塞 `bash_output` | 0 | 2 |
| 第一条调用为带固定 `sleep` 的 `bash` | 27（90%） | 0 |
| 其他工具或没有工具调用的正常回复 | 0 | 0 |
| 技术失败 | 0 | 1 |
| 整条回复出现固定 `sleep` 工具调用 | 27 | 0 |

C 的两次查看均为 `{"bash_id":"bg-10","block":false}`，没有用 shell 轮询。
一次上游 HTTP 504 没有返回首轮内容，按预定方案保留在 30 次分母中，没有重试补样。
其余 29 条有效回复全部选择 `bash_output`；其中 27 次为正确阻塞等待，2 次为查看状态。
按完整分母比较正确阻塞等待（3/30 对 27/30，将技术失败保留在未达目标一侧），
Fisher 双侧 `p≈2.82×10⁻¹⁰`。探索的 10 次不计入这个比较。

这轮证据支持把等待规则从单纯的回执文案提升为独立 harness 提醒：原始触发点的固定
`sleep` 从本轮对照的 27 次降到修复组有效回复中的 0 次。它没有证明任何模型、任何会话都不会
误选，也没有把两次非阻塞查看算成阻塞成功；验证范围仍是该位置的首轮工具选择。
