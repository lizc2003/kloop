# Plan 282 — DeepSeek 初审的轮数：先分清是模仿还是路由

> 2026-11-10 立。来源：plan 281 显示瓶颈在初审，两次撞上 80 轮上限；用户同意从初审入手。
> 状态：✅ 已完成（2026-11-10）。路由解释不成立；预载改动无收益（更慢、召回更低），不采纳。

## 现有数据（15 次真实提交初审：plan 272 的 11 次、plan 281 的 4 次）

- 每轮间隔中位数 3–11 秒，总时长基本由轮数决定。
- 单调用轮以读代码为主（主要是 bash `sed -n`，很少用 `read_file`），其次是搜索；读取里
  30%–90% 读的是本次改动的文件。
- **并发呈两极**：3 次运行（`72be062`、`9854970`、plan 272 的 R3-E）开头 6 轮全是单调用，
  之后 74–84 轮一次并发都没有，轮数 80–90（两次撞上限）；其余 12 次开头就有并发，后面
  也持续出现（例如 34/55、30/60）。同一 skill、同一提交的不同运行可以落在两边。
- 开局内容看不出诱因：单调用的三次第一轮都是一个用 `&&` 串命令的 bash 调用；`todo_write`
  不在开局。

## 两种解释与区分方法

1. **自我模仿**：开局单调用，后面照着自己的历史走。可以用中途提醒或开局示范打破。
2. **上游路由**：网关把部分请求路由到不支持（或模板压平）并发调用的后端。“全有或全无”
   的形态更像这种；提示词无效，只能换路由，或让单次调用做更多事。

**探针**（直接 Responses 请求，与 kloop 相同的 xhigh、`parallel_tool_calls: true`）：

- P-A 无历史：要求读取 4 个互不依赖的文件片段，只给一个读取函数，重复 12 次。
- P-B 历史示范：同一请求前放一轮已完成的读取，分别示范“1 个调用”和“3 个调用”，各 6 次。
- 每次记录函数调用个数和响应 usage 里的上游路由标识。路由名属于上游内部信息，只在
  本机比较，仓库里用中性代号。

判读：若单调用集中在某个路由、且同一路由内与历史示范无关 → 路由；若与示范强相关、
与路由无关 → 自我模仿；两者都有则分别报告。

## 结果

### 探针（2026-11-10）

24 次请求（无历史 12 次、示范“逐个调用”6 次、示范“一次三个”6 次）**全部一次发出 4 个
调用**；观察到两个上游路由，两边都正常并发，示范逐个调用也没压住并发。

- **路由解释不成立**（至少对观察到的两个路由）；一轮历史示范也压不住并发。
- 真实审查里的单调用更可能来自任务形态：探针里的 4 个读取事先已知、互不依赖；审查是
  读一段、想、再决定读哪里的串行探索。单调用的运行也会在一个 bash 调用里一次 diff
  多个文件，只是之后逐段 `sed -n` 往下读。靠提示让模型“多并发”是在跟任务形态较劲。

## 第二阶段：预载改动（请求前冻结）

读取里 30%–90% 落在本次改动的文件上。把改动连同完整函数一次放进开头的提示，这部分
轮次不依赖模型听话就能省掉。

- **P 组**：同一 skill 正文之后追加预载：diff stat；`*.rs`/`*.py` 用 `git diff -W`（内置 rust、
  python 函数识别，每处改动带完整函数）；其余文件 3 行上下文；并说明只需另读改动之外的
  调用方、被调用方、测试与依赖定义。规模：样本提交 15K–152K 字符（代码部分）。
- **A 组**：当前 `/code-review`，不预载。两组快照仓库都写入同样的 diff 属性，只差预载。
- **样本**：plan 281 的四个提交（`418f953`、`72be062`、`b78ae41`、`9854970`），每个提交 A、P
  同时并行各跑一次；`review-bench.py run --commit`，release 二进制，轮数上限两组都放宽到
  120（测真实轮数，不记撞线）、3,600 秒。不重试、不换样。
- **指标**：交付、轮数、墙钟、输入/输出 token、单调用轮比例；报告是否给出已知缺陷
  （K1–K5 见 plan 281，另加 `418f953` 的 `--split-s` 缩写绕过）。
- **采纳条件**：P 组墙钟中位数 ≤ A 组 0.8 倍；交付数 ≥ A；命中的已知缺陷数 ≥ A；
  撞上限次数 ≤ A。全部满足才进入下一步（含是否影响其他模型的决定）；否则记无明确收益。
- 冻结摘要前缀：`scripts/review-bench.py` `a9e0a7a8ccf00150`，`SKILL.md` `f20a30bccab9c3a6`，
  release 二进制 `c6b2c50321e927fd`。

### 第二阶段结果（8 次初审，全部交付，无一撞上限）

每行：墙钟分钟 / 轮数 / 工具调用 / 输出 token / 输入 token（含缓存）。

- `418f953`：A 11.1 / 66 / 105 / 98K / 6.4M；P 12.1 / 73 / 102 / 99K / 7.8M
- `72be062`：A 7.3 / 29 / 51 / 71K / 1.9M；P 11.6 / 47 / 74 / 94K / 4.4M
- `b78ae41`：A 11.9 / 44 / 69 / 87K / 3.5M；P 12.5 / 42 / 52 / 91K / 3.9M
- `9854970`：A 8.0 / 57 / 83 / 57K / 4.6M；P 6.6 / 49 / 75 / 50K / 5.3M

墙钟中位数 A 9.6 分钟、P 11.9 分钟（P/A = 1.24），四个提交里三个 P 更慢。

已知缺陷（6 个）：A 4/6，P 2/6。

- `418f953`：A 三条都报（未知选项之后的 `-S`、长选项缩写、`-uSSH_AUTH_SOCK` 误拒）；
  P 报了前两条，漏了误拒。
- `72be062`：两组都没找到 K3。
- `b78ae41`：A 调查过 K4（`env -a`），以“构造不出实际错误输出”排除；P 未提。
- `9854970`：A 报出 K5；P 漏了。

**结论：按冻结条件不采纳预载。** 墙钟、召回两项都不满足，P 还多读了 10%–130% 的输入。

**单调用模式这次没有出现**：8 次全部从开头就并发（多调用轮 11/42 到 40/66）。合计
plan 272 有 1/11、plan 281 有 2/4、本轮 0/8、探针 0/24。单调用一旦出现就贯穿整次运行，
且集中在某段时间，更像上游某段时间的状态，而不是 skill 或任务能控制的；现有数据不足以
定论，也不值得为它改提示。同一提交的轮数可以差到 29 对 80，单次对照很难测出小改动的
差别。

**顺带发现并已修复的安全问题**：`418f953` 的 A、P 两份报告独立报出——plan 272 的“双视图”
只补了危险判定，deny/ask 规则仍只看 value 视图，`for w in rm; do env "$w" -rf build; done`
在 bypass 下绕过 `bash(rm *)` deny（实测放行）。修复见同日提交。
