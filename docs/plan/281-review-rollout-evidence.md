# Plan 281 — 复核证据换成初审实际读过的代码

> 2026-11-10 立。来源：plan 276 的自动复核没有可验收的新增缺陷，反而出了误报；误报的
> 共同点是证据不足（固定窗口没带到调用方或依赖语义）。用户同意先在循环外验证：
> 复核时改用初审在 rollout 里实际读过的代码当证据，能否减少误报、救回错误排除。
> 状态：✅ 已完成（2026-11-10）。按冻结规则记为“无明确收益”，停止这条线；结果见末节。

## 约束

- 遵守 plan 230：不进共享 agent 循环、不改内置 skill 与 `/code-review` 默认行为。
- 不重试、不换样、不按结果改问题或规则；全部失败与成本保留。
- 判分由人工按冻结源码进行，判分者知道修复提交的答案；结论只说明这批样本。

## 协议（请求前冻结）

**样本**：四个未用于 plan 272–280 的历史提交，每个都有后续修复提交确认的缺陷。

- `418f953`（修复 `72be062`）：K1 未知 `env` 选项之后的 `-S` 不再检查（`env --debug -S
  'cat .env'` 放行）；K2 簇里含 `S` 即判 split-string，`env -uSSH_AUTH_SOCK cargo test`
  被硬拒。
- `72be062`（修复 `b78ae41`）：K3 `env -iuSSH_AUTH_SOCK sh -c 'cat .env'` 走不完整包装器
  分支，`sh -c` 正文不分析，bypass 放行。
- `b78ae41`（修复 `75a2efa`）：K4 `env -a -bash bash -c 'cat "$HOME/…"'` 让 bash 成为登录
  shell，嵌套分析仍把 HOME、cwd 当已知。
- `9854970`（修复 `3e515c9`）：K5 同一 profile 把签名策略从 optional 改回 required 时
  路由身份不变，含无签名推理的历史在 required 下被拒，采样与压缩一起卡住。

**两组共享同一次初审**：每个样本跑一次 `pipeline`（release 二进制、本机正常配置、
实际捕获的采样、内置 skill + 账本要求），它同时完成 A 组复核：plan 276 的固定窗口
（锚点前后 80 行、按行差异映射另一版本、160,000 字符）、无工具、单次独立请求。
之后用新入口 `rollout-recheck` 对同一份账本做 B 组复核，**只换证据**：同一批 excluded
候选与问题、同一提示、同一采样、同一字符预算、无工具、单次请求、不重试。

**B 组证据提取规则**（只认能定位到冻结行号的读取，其他命令不计）：

- `read_file` 返回内容里的行号（after 版本）；
- 任一输出里的 git 补丁：按 hunk 逐行，只计实际显示的行（` ` 两版本、`-` before、`+` after）；
- `sed -n 'A,Bp' 文件`、`nl … 文件 | sed -n 'A,Bp'`、`cat 文件`（after）；
  `git show REV:文件 | sed -n 'A,Bp'` 与不经过滤的 `git show REV:文件`（REV 在初审快照里
  解析为父版本或目标版本）；
- `grep`/`rg`/`git grep` 与 grep 工具输出里的 `路径:行号:`（单文件时 `行号:`），只计匹配行。

只保留对应版本 Git blob 中真实存在的路径与行；间隔不超过 3 行的行合并成一段。超出
预算时，先取 excluded 候选锚点所在文件的段，再按首次读取顺序取其余文件的段，整段
取舍、不截断，丢弃的段记录在包里。每个 excluded 候选都可引用全部 B 证据。

**判分**：每个 excluded 候选按冻结源码人工判定是否为本次提交引入或加重的缺陷：已知
缺陷 K1–K5 以修复提交为准，其余逐条读代码并写明理由。两组分别统计：救回的真缺陷、
误报确认、unresolved、整包交付、复核输出 token、复核耗时。

**采纳条件**：B 组同时满足以下全部条件，才进入后续验证（仍不默认接入）：

1. 救回的真缺陷 ≥ A 组；
2. 误报确认 ≤ A 组；
3. 前两项至少一项严格更好；
4. 整包交付数 ≥ A 组；
5. 复核输出 token 合计、复核耗时合计都不超过 A 组的 1.5 倍。

否则记为“无明确收益”，停止这条线、不再加机制。若四个样本的 excluded 里都没有真
缺陷且两组都没有误报，记为“不可判”。

**冻结的执行环境**：`pipeline` 默认参数（80 轮、3,600 秒、上下文 80 行、160,000 字符），release 二进制（sha256 前缀 `c6b2c50321e927fd`），同时最多两个样本；脚本 sha256 前缀：

- `scripts/review_rollout.py` `58e2e99831a2ccf5`
- `scripts/review_pipeline.py` `c69bb13f06df0434`
- `scripts/review_recheck.py` `23d16bac09989042`
- `scripts/review-bench.py` `2418edacf995f731`
- `rust/crates/core/src/skills/code-review/SKILL.md` `f20a30bccab9c3a6`

**执行中的偏差（如实记录）**：`rollout-recheck` 的配对检查最初只认“A 组发过请求”，把“账本已保存、A 组在证据准备阶段失败”（`418f953` 的固定窗口超预算）也挡在外面，比协议更严。改为允许这种情况，B 组的取证、组包与请求代码不变，补测试；`scripts/review_rollout.py` 新摘要前缀 `40917f44b8fe5391`。只为 `418f953` 补跑这一次 B 组（此前未发过 B 组请求，不是重试）。

**局限**：样本少；前三个提交改的是同一函数，彼此相关；初审只跑一次（两组共享，
初审本身的方差不在比较内）；判分者知道答案。

## 实测结果

### 交付与成本

- **初审**（两组共享）：
  - `418f953`：交付，13.3 分钟、61 轮、100 次工具调用，输出 107K token；账本 2 确认、8 排除。
  - `b78ae41`：交付，21.4 分钟、73 轮、90 次调用，输出 175K；账本 1 确认、8 排除。
  - `72be062`：80 轮上限，17.1 分钟，80 轮只有 80 次调用（每轮一个），无报告与账本。
  - `9854970`：80 轮上限，9.1 分钟，同样每轮一个调用，无报告与账本。
  按协议不提高上限重跑、不换样；这两个样本两组都无法比较。
- **A 组**（固定窗口）：`418f953` 8 个候选的窗口合计 175,385 字符，超过 160,000，未发请求；
  `b78ae41` 发出 1 次，281.5 秒，输出 38,383（推理 37,345），响应完成但 C9 引用了只授权
  给其他候选的来源，整包校验失败。
- **B 组**（初审实际读过的行）：`418f953` 取 236 段中的 76 段，224.6 秒，输出 29,454；
  `b78ae41` 取 159 段中的 59 段，205.1 秒，输出 29,733。两次响应都完成，但各有一条引用
  越出来源的行范围，整包校验失败。

整包交付：A 0/2，B 0/2。已交付的包里，救回的真缺陷与误报确认两组都是 0。

### 判分（逐条对照冻结源码）

- 已知缺陷：K2 和 `--split-s` 长选项缩写绕过（同由 `72be062` 修复）被 `418f953` 的初审
  直接确认；K1、K4 没进账本（初审没调查）；K3、K5 所在样本初审未交付。**复核无从救回
  任何一个已知缺陷。**
- 两组都排除的候选里，按“本次提交引入或加重”的定义有两条真问题：`418f953` C7（沙箱
  升级获批后重跑，第一次运行落盘的截断全文无人引用，留下孤儿文件，影响很小）；
  `b78ae41` C9（HANDOFF 教训 357 把 `xargs -r` 当成不完整包装器的例子，但 `-r` 已建模，
  例子错误）。其余排除都成立。
- 不计分的内容观察（包未交付）：B 组在 `418f953` 确认 C4、C5、C7，在 `b78ae41` 确认 C4；
  A 组 `b78ae41` 全部维持排除。C4 两处都是 `exec` 后接 shell（`exec env -S …`、`exec sh -c …`）
  绕过敏感读取硬拒绝，在 HEAD 上实测成立（`exec`、`builtin exec`、`command exec` 均放行）。
  它早于这两个提交，按本计划的判分定义不算本次提交的缺陷；但复核提示沿用 plan 273 的
  定义（“修复所声称范围里漏掉的具体路径”也可确认），按那个定义 B 组是对的。判分定义
  与提示定义不一致，是本计划的设计缺口。C5（`env -S 'ls -la'` 被拒）是 plan 272 写明
  接受的代价，计为误报；C7 是真问题。

### 复审更正（2026-11-11）

- B 组证据提取曾按命令写的范围记 `sed -n`/`cat`/`git show` 读取，没看输出是否真的显示了这些行（截断、`| head` 过滤、没执行的条件分支都会多算）。改为按内容核对：按命令顺序在输出里找对应冻结行从第一行起的最长连续前缀，只计这一段；会话落盘预览不计。用修正后的解析器重算本计划两份 rollout：`b78ae41` 有 91 行命令范围没有完整显示，但 B 组包里不能确认显示过的只有 11 行（`418f953`，0.3%）与 3 行（`b78ae41`，0.1%），结论不受影响。
- `rollout-recheck` 曾无条件走普通独立请求；若 A 组用结构化裁决、文本交付或补查，两组就不止证据一个变量。本计划的 A 组都是默认设置，不受影响；入口改为与 `pipeline` 共用同一套按冻结协议的复核分派。

### 结论

- **按冻结的采纳条件：无明确收益。** 第 3 条（至少一项严格更好）不成立，停止这条线，
  不再增加机制，`rollout-recheck` 留作开发入口。
- 真正的瓶颈在初审，而不在排除复核：一半样本撞上轮数上限，且每轮只发一个调用；已知
  缺陷大多根本没被调查。复核只能改判已调查的候选。
- 复核这一步当前的主要障碍是交付：三次发出的请求都只因一条引用越界或越权而整包作废。
  事后看，若按候选逐条接受，B 组在两个样本都能保住对 `exec` 绕过的确认（`418f953` 的那条
  恰好是坏引用所在，会被丢掉）。这是事后分析，不计入结论。
- 实验顺带确认的产品问题：`exec`/`builtin`/`command exec` 后接 shell 的敏感读取绕过
  （安全，同日修复：包装器分析剥离 `exec [-cl] [-a name]` 与 `builtin`，危险命令审批随之
  恢复）；教训 357 的错误例子（文档，同日改正）；沙箱升级后的孤儿落盘文件（2026-11-11
  修复，同时修了 stdout 超过内联上限时沙箱拒绝判定看不到 stderr 拒绝行的旧问题）。
