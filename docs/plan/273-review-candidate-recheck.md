## 范围与约束

- 沿用 plan 272 的 DeepSeek 模型与 high effort，真实 API 的代理和 key 由用户指定。
- 尊重 plan 230 的回退决定：不新增原生 review 阶段，不给核心循环增加审查状态。
- 以现存历史报告中的被排除候选为开发样本；未参与提示设计的另一提交作为留出样本。
  候选人工整理，记录来源；不能把这种实验的结果当作端到端审查召回率。
- 初审结论、排除理由、标准答案和后来的修复代码不进入复核请求。请求只包含中性的
  候选问题、固定父版本/目标版本的代码片段与行号。候选问题本身也不是已证实的事实。
- 每组候选合并为一次无工具、无历史的 Responses 请求。只有非空候选组才请求；每组
  每次最多一个请求，失败不重试、不补样、不让模型续查。片段预算超限则在请求前拒绝，
  不静默截断。缺证据返回 unresolved，不自动当作缺陷或无缺陷。
- confirmed 的严重度与是否确定分开；confirmed 和 excluded 都必须引用所给代码。
  结构校验只能检查引用有效，事实正确性仍需人工核对。

## 采样前冻结的协议

- 提示、样本、代码片段、真值及请求摘要在真实请求前准备并冻结。开发样本的旧报告只用于
  取候选，不能用已知答案补写触发输入；原候选未提出的条件保留为缺口。
- 第一批使用 plan 272 的 R1、R4、R3 历史候选；在提示固定后选择另一提交制作留出样本。
  混入有代码依据的无缺陷候选，避免只提供正例。留出样本也由人整理，不能消除选择偏差。
- 每组预定 3 次独立请求，共用同一份冻结正文；每次最多 120 秒、8,192 输出 token，
  请求正文上限 80,000 字符。请求失败、输出不完整、格式错误均记失败，不改记 unresolved。
- 指标：原来漏报的已知缺陷被 confirmed 的数量、无缺陷候选被误升为 confirmed 的数量、
  unresolved、失败数、墙钟与实际 usage。重复试验按候选×试次报告，另列独立候选数；
  不把重复采样当作更多独立缺陷。
- 所有 promoted finding 按冻结代码人工复核；有效 JSON 和模型自称有证据都不等于命中。
- 是否值得落地看开发及留出样本是否都能救回缺陷、是否引入误报，以及附加耗时。
  以原完整审查墙钟的约 10% 为速度参考，不以增加 findings 数量本身判成功。
- 原始请求/响应与历史报告留本机临时目录；仓库只记录协议、可复用脚本、回归与汇总。

## 真实结果（2026-11-09）

共 12 次预定请求，8 次产生有效裁决，4 次以 `response.incomplete` / `length` 结束。
这 4 次都把 8,192 个输出 token 全部用于推理，没有任何裁决正文；无超时或格式校验失败。
保留失败，不从部分推理提取裁决，也不提高预算后重跑。

| 组 | 有效请求 | 已知缺陷确认次数 | 对照正确排除次数 | 单次中位耗时 |
| --- | ---: | --- | ---: | ---: |
| R1 | 3/3 | 缓存计数容器错型：3/3 | 3/3 | 35.0 秒 |
| R4 | 2/3 | 迟到工作跳过：2/3；压缩前估算误记：2/3 | 2/3 | 61.1 秒 |
| R3 | 0/3 | 启动选项导致误拒：未交付裁决 | 0/3，未交付裁决 | 60.2 秒 |
| 留出 | 3/3 | thinking 完成时缺签名：3/3 | 3/3 | 52.9 秒 |

上表分母包含失败请求；R4 的同一次失败同时使两个缺陷和一个对照未被判断，不能算作
“排除”或“没有问题”。开发组 4 个历史缺陷，在三次试验中分别救回 3、1、3 个；按至少一次
确认计为 3/4，但一次生产复核没有三次取并集的预算。留出缺陷三次都确认，不能记成历史漏报。

人工逐条核对全部 18 个已交付裁决：10 次缺陷确认、8 次正确排除，没有发现错误裁决。
10 次确认对应 4 个独立缺陷（历史 3 个、留出 1 个）；8 次正确排除只对应 3 种独立对照，
R3 的第 4 种对照从未交付裁决。未观察到误报不等于证明没有误报风险，也没有实际交付的
unresolved 样本可用于检验证据不足时的表现。

被救回的历史缺陷不再用“文档说缺失即零”“计划只要求 EndTurn”“偏保守”等理由排除：
R1 三次都追到错型容器由错误变成零计数；R4 两个有效请求都追到结构化结束前漏掉最后的
迟到工作检查，以及压缩前估算让已拒绝上限偏大。对应代码与后续修复独立核对，裁决成立。
留出组也能追到签名缺席、完成块交付和序列化省略空签名的整条路径；初始签名前缀则由
`push_str` 保留，正确排除。

12 次请求耗时 34.6–63.2 秒，中位 55.9 秒；各请求时长合计 631.3 秒（有并发，不能当作
整批墙钟）。总输入 67,122 token（含缓存），输出 82,623 token，其中推理 79,612，约占
输出的 96%。按原报告墙钟作粗略参考，单次中位附加时间约为 R1 的 5.1%、R4 的 10.5%、
R3 的 4.6%；留出组没有对应的完整审查耗时。手工整理候选和选取代码片段的成本不在这些
请求时长中，不能据此承诺生产流程的总开销。

## 结论与取舍

- 在这批人工准备的候选和证据上，独立复核能纠正一部分初审的错误排除；收益有代码依据。
  但问题重述、片段筛选和独立请求同时变化，不能把收益单独归因于“多一个裁决阶段”，
  更不能当作整个审查召回率已提升。
- 当前配置下 4/12 请求没有交付裁决，R3 全部失败；短输入不保证短推理。即使成功组没有
  误报，也不适合默认给每次审查追加这个步骤。保留可显式运行的实验入口，不改生产流程。
- 下一步若继续，应先验证怎样在既定时间和输出预算内可靠交付（包括明确 unresolved），
  并检查自动准备候选和证据的成本；需要新协议和留出样本，不能通过扩大预算重跑本批
  失败来改写本次结果。当前实验到此完成。

本次只进行真实 API 实验和文档更新，没有修改 Python/Rust 代码。验证包含四份实际请求与
冻结包一致、仅一个 user 输入、无工具和答案标签、引用仅来自父版本/目标版本，以及全部
已交付裁决的人工代码核对；运行 `recheck-stats`、`git diff --check` 和暂存差异检查。
没有重新编译或跑测试套件。
