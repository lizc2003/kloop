# Plan 273 — 独立复核被排除的审查候选

> 2026-11-09 立。用户同意先做独立实验：验证短上下文复核能否救回 plan 272 中
> 已调查却被排除的缺陷，同时检查误报和耗时，再决定是否进入实际审查流程。
> 状态：实验准备已完成，真实 API 采样待用户指定配置。实验入口限于 benchmark 脚本；
> 不改变内置 skill 或共享 agent 调度。

## 范围与约束

- 沿用 plan 272 的 DeepSeek 模型与 high effort，真实 API 的代理和 key 由用户指定。
- 尊重 plan 230 的回退决定：不新增原生 review 阶段，不给核心循环增加审查状态。
- 以现存历史报告中的被排除候选为开发样本；未参与提示设计的另一提交作为留出样本。
  候选人工整理，记录来源；不能把这种实验的结果当作端到端审查召回率。
- 初审结论、排除理由、标准答案和后来的修复代码不进入复核请求。请求只包含中性的
  候选问题、固定父版本/目标版本的代码片段与行号。候选问题本身也不是已证实的事实。
- 每组候选合并为一次无工具、无历史的 Responses 请求。只有非空候选组才请求；每组
  每次最多一个请求，失败不重试、不补样、不让模型续查。片段预算超限则在请求前拒绝，
  不静默截断。缺证据返回 unresolved，不自动当作缺陷或无缺陷。
- confirmed 的严重度与是否确定分开；confirmed 和 excluded 都必须引用所给代码。
  结构校验只能检查引用有效，事实正确性仍需人工核对。

## 采样前冻结的协议

- 提示、样本、代码片段、真值及请求摘要在真实请求前准备并冻结。开发样本的旧报告只用于
  取候选，不能用已知答案补写触发输入；原候选未提出的条件保留为缺口。
- 第一批使用 plan 272 的 R1、R4、R3 历史候选；在提示固定后选择另一提交制作留出样本。
  混入有代码依据的无缺陷候选，避免只提供正例。留出样本也由人整理，不能消除选择偏差。
- 每组预定 3 次独立请求，共用同一份冻结正文；每次最多 120 秒、8,192 输出 token，
  请求正文上限 80,000 字符。请求失败、输出不完整、格式错误均记失败，不改记 unresolved。
- 指标：原来漏报的已知缺陷被 confirmed 的数量、无缺陷候选被误升为 confirmed 的数量、
  unresolved、失败数、墙钟与实际 usage。重复试验按候选×试次报告，另列独立候选数；
  不把重复采样当作更多独立缺陷。
- 所有 promoted finding 按冻结代码人工复核；有效 JSON 和模型自称有证据都不等于命中。
- 是否值得落地看开发及留出样本是否都能救回缺陷、是否引入误报，以及附加耗时。
  以原完整审查墙钟的约 10% 为速度参考，不以增加 findings 数量本身判成功。
- 原始请求/响应与历史报告留本机临时目录；仓库只记录协议、可复用脚本、回归与汇总。

  原始响应保留在本机输出目录，自动标签匹配之后仍须人工复核。
