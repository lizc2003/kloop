## 调研：opencode 的审查链路

- `/review` 是一段 4.5KB 的提示，作为用户消息注入（`packages/core/src/plugin/command/review.txt`）。
  三个要点：
  1. 工作区审查先跑 `git status --short`，把**未跟踪的新文件全文读一遍**。
  2. “Diffs alone are not enough”——**读被修改文件的全文**，再查规约文件。
  3. 一张明确的“找什么”清单：逻辑与边界错误、缺失的判断、空值与错误路径、竞态、注入与
     越权、吞掉错误的处理、该用而没用的现有抽象、明显的性能问题、行为变化（尤其可能
     无意的）。
- DeepSeek 没有专属系统提示，走 756 字节的默认版本（`session/runner/prompt/system.txt`）；
  模型专属提示只给 gpt、claude、kimi 等。
- shell 输出超过 50KiB/2000 行时只留尾部，**完整输出存文件并给出路径**（`packages/core/src/shell.ts`）。
- Chat 协议把 `reasoning_content` 回传给模型（`packages/ai/src/protocols/openai-chat.ts`）。
- 读文件时向上发现子目录的 AGENTS.md 并注入（`tool/plugin/read.ts`）。
- 没找到修剪旧工具输出的机制；`/goal` 的 judge 要手动开启，不参与默认审查。
- 审查提示建议用 Explore 子 agent 和网络搜索。kloop 实测过这两样的代价（plan 119：
  fork 出去的审查 42 分钟、254 次工具调用；另一次审查 65 次网络搜索），**不借鉴**。

## kloop 的差距

- **G1 未跟踪文件**：skill 只写 “review the working tree against HEAD”，`git diff HEAD`
  不显示未跟踪文件，新增文件整个不在审查范围里。
- **G2 没有缺陷清单**：skill 的篇幅在流程（目标解析、冻结 SHA、候选结论），没有分类。
- **G3 bash 截断不可恢复**：`tools/bash.rs` 只留前 30,000 字符，其余丢弃；它低于
  `history::OFFLOAD_CAP_CHARS`（32,000），所以现有的落盘机制对 bash 从不生效。大的
  `git diff` 被截断后，后半段只能重跑。
- **G4 读全文还是宽 diff**：plan 128 在 gpt-5.6-sol 上实测，read_file 行数越多轮数越多
  （630/1250/1360/2280 行 → 5/12/17/60 轮），因此 skill 让模型取宽上下文 diff、不开整个
  文件。这组数字没有在 DeepSeek 上验证过。
- **G5 推理回传**：Chat 轨按设计不回传推理（DESIGN「OpenAI Chat keeps its existing
  intentional boundary」）；本机 DeepSeek 走 Responses 轨，kloop 把推理放进 `summary`
  和 `encrypted_content` 发回，但网关有没有交还给模型，代码里看不出来。
- **G6 base 提示重复**：BASE_SYSTEM 9,514 字节，其中“专用工具优先”“先进 plan mode”
  “委派条件”“提问条件”与对应工具描述重复，几条长条目可压缩，估计能减约 2KB 而不丢规则。

## 改进项

- **P1（G1）**：skill 的无目标分支补一句：先用 `git status --short` 列出未跟踪文件，
  新文件全文读、算进改动清单。只改 skill 文本。
- **P2（G2）**：skill 加一节 “What to look for”，列 opencode 那张清单，并写明这是在
  **已经读到的内容里**找，不额外引出动作。性能问题只报无界数据上的；行为变化要报，
  按 skill 现有的 “deliberate 与 correct 是两个问题” 处理。
- **P3（G4）**：把“不开整个文件”改成按大小分：被改文件不超过 N 行就整文件读，否则取
  宽上下文 diff。N 开工时按实测定（初值 400）。
- **P4（G3）**：bash 输出被截断时，把已捕获的完整输出写进 offload 存储
  （`cfg.offload_dir` + `history::write_offload_file`），在截断标记里给出路径与行数；
  内联部分保持 30,000 字符不变，所以不增加上下文。流捕获上限（150,000 字节）是否放大，
  开工时定。代码改动，需要回归测试。
- **P5（G5）**：先做直接 API 探针：第一次请求让模型只在推理里记一个随机数，第二次
  请求带上 / 不带上推理项，问它记的是什么。带上能答对、不带上答不对，才说明网关真的
  把推理交还给模型。结果决定要不要再查。
- **P6（G6）**：精简 BASE_SYSTEM，删除与工具描述重复的句子，压缩长条目，保留所有实测
  来源的条款。

## 实测设计

- **基准仓库**：`scripts/review-bench.py make <dir>` 生成一个 Python 小项目，工作区里带
  一组未提交改动（含一个未跟踪的新文件）。审查目标是“无参数 = 工作区”。
- **预埋缺陷**（判分标准：报告给出正确位置和成因记 1 分；位置对、成因含糊记 0.5；
  没报记 0）：
  - D1 分页 off-by-one，在 diff 里（基础题）。
  - D2 `parse_amount` 改为返回分，未修改的调用方仍按元乘 100（要找 diff 外的调用方）。
  - D3 新增字段写进了 `to_dict`，同文件约 150 行外的 `from_dict` 没跟上（要读 diff 外的
    同文件内容）。
  - D4 配置加载吞掉所有异常返回空字典，使币种白名单失效（吞错误 + 安全后果）。
  - D5 未跟踪的新文件里有路径穿越（考 G1）。
  - D6 重试循环在限流分支不递增计数，可能死循环；该文件在 diff 里排在一个约 40K 字符的
    数据文件之后（考 G3）。
  - D7 重构排序键时丢了 `reverse=True`，文档仍写“最新在前”（考行为变化）。
  - D8 去重从集合改成列表，报表全量数据上变成 O(n²)（考性能类）。
  - 诱饵：一个看起来像 off-by-one 的向上取整分页数，实际正确。报了算误报。
- **对照组**（同一基准、同一 provider，各跑 N 次）：
  - A 基线：内置 skill + 内置 base。
  - B opencode 提示移植：`review.txt` 原文作为 skill + 内置 base（只隔离提示词这一变量）。
  - C 改进 skill：内置 skill + P1、P2、P3 + 内置 base。
  - D C + 精简 base（P6，经 `system_prompt_file` 注入）。
  - P4 要改代码，第一轮不测；基线里统计截断事件，判断它在实际审查里出现的频率。
- **运行方式**：release 二进制，`--headless --json --max-rounds 80`，默认权限模式
  （无审批人，任何需审批的调用自动拒绝，各组一致）。提示为 skill 正文展开后的文本，
  与 TUI 里 `/code-review` 得到的一致；同时把该组的 skill 放进基准仓库的
  `.kloop/skills/code-review/` 覆盖内置版本（并加进 `.git/info/exclude`，避免它自己成了
  未跟踪文件）。每次运行用临时 HOME，配置从本机复制，结束后删除。
- **指标**：每个缺陷得分、召回（满分 8）、误报数、轮数、工具调用数、墙钟、输入/输出
  token、bash 截断事件数。
- **局限**：没有 opencode 本体对照组（本机未安装，网关的 Chat 路由对部分 DeepSeek 模型
  返回 403，见 plan 163）；基准是合成的；N 小，只能看方向。

## 实测结果

### P5 推理回传探针（2026-11-09）

本机 DeepSeek provider（Responses 轨，`deepseek-v4.1-flash-1017`，effort high），
`scripts/review-bench.py probe-reasoning`。

- **第一版探针无效**：让模型自己在推理里选随机数，结果推理只有 71–109 字符、里面没有
  数字，回答也无从对照。改为在历史里放合成推理项。
- **跨轮测不出**：把推理项放在上一条用户消息之前，带不带推理都答 “unknown”（3/3）。
  DeepSeek 的对话模板本来就丢弃更早轮次的推理，这个位置不能用来判断回传。
- **轮内回传生效**：推理项放在当前轮的工具调用之前（审查时多轮工具调用就是这个形状）：

  - kloop 现在的形状（文本在 `summary`，`encrypted_content` 为空）：4/4 答对暗号。
  - 文本放在 `content` 的 `reasoning_text`：3/4 答对。
  - 不带推理项：0/4，全部 “unknown”。

**结论：G5 不成立**，网关会把 kloop 回放的轮内推理交给模型，P5 不改代码。

### 真实提交（2026-11-09，每组 1 次）

合成基准测不出召回差异，改用 kloop 自己历史上“提交后被审查发现缺陷、随后有修复提交”的
改动，以修复提交为标准答案。审查仓库只含父版本快照和该提交（`run --commit`），修复提交
不在对象库里。审查目标为 `HEAD`。

- **R1 = `a41f6c7`**（provider 流式读取；修复 `389a663`）：K1 Messages 的 usage 用
  `serde_json::Map` 下标取值，缺键 panic；K2 Chat 终端帧之后 `Err(_)` 全吞，完整坏帧、
  超限也被接受，与文档的 fail-closed 承诺不符；K3 缓存明细容器类型不对时被链式下标
  读成 Null、记为未命中（改前会报错，属回归）。
- **R4 = `6cc14b8`**（agent 循环；修复 `0deab95`）：K1′ 已校验的结构化值在 EndTurn 时
  跳过迟到消息检查，消息随租约关闭被拒；K2′ 截断链被工具轮打断后，错误出口仍用已清空
  的前缀拼文本，丢段；K3′ 被拒时记录的是压缩前的估算。

结果（命中 / 已知数，墙钟，轮数，输入 token 含缓存，输出 token）：

- R4：A 1/3（K2′），9.7 分，56 轮，5.2M，70K；B 1/3（K2′），7.3 分，44 轮，3.2M，55K；
  C 2/3（K1′、K2′），11.2 分，56 轮，5.5M，84K。
- 三组都额外报了同一条：`/context` 的逐块明细仍按 base64 字节估算图片
  （`commands/context.rs` 的 `block_tokens`），与同一命令的 history 行和 DESIGN 矛盾。

每格只有 1 次，2/6、3/6、3/6 之间的差异不能下结论。**可以下结论的是漏报的形态**：

- kloop 两组漏掉的 7 个已知缺陷里，**6 个是调查过、然后写进 Excluded**：A 把 R1 K3

所以 DeepSeek 在 kloop 里丢召回，**主要不在覆盖，而在排除那一步**。这也解释了同事的感受：
同一个问题，opencode 列成低严重度发现，kloop 写进 Excluded，读起来像“不是问题”。

代价方面：C（P3 整文件读）在两个真实提交上都比 A 慢 9–15%、输入 token 多 6–66%，
召回没有可见收益。

### 由此新增 P7，并调整候选组合

- **P7**：Excluded 只在“失败不会发生”时成立。能写出输入到错误输出的场景（panic、坏值被
  当成好值、错误被吞、消息被丢、改动自己的文档承诺而代码没做到），就是 downgraded，
  以低严重度进 findings。“计划如此”“与新文档一致”“偏保守”“实际不太可能”“旧代码也
  好不到哪去”都是严重度的理由，只决定排在哪，不决定报不报。“已有问题”指同一输入在
  改动前就到达同一错误输出。不增加任何动作：调查本来就做了。
- **E 组** = 内置 skill + P1 + P2 + P7（去掉 P3，因为它多花时间而没有收益）。在 R1、R4
  上各跑一次（样本内），再加一个样本外提交 R3 = `85d7a2b`（shell 选项解析；修复
  `eba8429`）：K1″ 选项簇里每个 `o` 都按“吃下一个词”计，zsh 却把簇的剩余部分当 `-o`
  的值，`zsh -c -oshwordsplit 'cat .env' unused` 被判为非 -c 模式、敏感读取放行；K2″ 第一个
  选项不是单独的 `-c` 就把启动文件判为未知，`bash -euo pipefail -c 'cat "$HOME/x"'` 被硬拒。
  R3 上跑 A、B、E。

### 汇总与结论

已知缺陷命中（三个真实提交，合计 8 个）：A 3/8，B 4/8，C 3/6（未跑 R3），E 3/8。

1. **同事说的“更完备”没有在召回上复现。** 真实提交上 B 比 A 多 1 个（N=1，在噪声内）；
   合成基准上 kloop 9 次全满分，B 3 次里漏了 1 次。可复现的差别有两个：B 把次要问题
   列成 Low 报出来（kloop 写进 Excluded），以及 **B 更快**：合成基准约快 3 倍、输出 token
   约为 1/3；真实提交快 25–37%、输出 token 少 0–42%。快的来源是 kloop skill 要求用实验
   验证结论，B 大多只读。
2. **单次审查只找到约四成，而且每次找到的不一样。** 四组单次命中都在 1/3–2/3，但八个
   已知缺陷里有七个至少被某一组找到（只有 R4 的 K3′ 谁都没报）。方差比组间差异大得多，
   N=1 的组间比较不能用来选方案。
3. **kloop 的漏报主要出在排除那一步，文字规则管不住。** A、C、E 漏掉的 13 个里有 12 个是
   调查过再写进 Excluded；原 skill 已经禁止“拿改动自己的文字当排除理由”，P7 又把它写得
   更具体，E 组仍有 3 次正是这样排除的。对 DeepSeek，靠追加文字条款改不了这一步。
4. **P5 不是原因**（轮内推理回传生效）；**P6 没有可见影响**；**P3 只增加代价**；P1、P2 在
   合成基准上测不出（天花板），在真实提交上看不出（噪声）。
5. **diff 截断经常发生**：真实提交的 11 次运行里有 6 次 diff 被截断（含 A、E 组），被截掉的
   部分最多 39K 字符，只能重跑才拿得到。这次测不出它对召回的影响，但发生频率支持 P4。

### 取舍

- **采纳 P4**（bash 截断落盘给路径）：发生频率高，内联大小不变，不增加上下文和轮数。
  需改代码、补回归。
- **采纳 P1**（skill 写明未跟踪文件）：零成本，修的是文字本身的缺口；模型这次都自己做到了，
  收益小。
- **不采纳 P2、P3、P6、P7**：P3 只增加代价；P2、P6、P7 没有测出收益，P6 还会影响其他 provider。
- **P5 关闭**：不需要改动。
- **待定的方向（需要用户拍板，且要新实验）**：
  - **排除复核**：既然漏报集中在 Excluded，而文字规则无效，可以把“复核排除清单”做成
    结构性的一步，例如报告写完后用一个短回合只看 Excluded 里带失败场景的条目。会增加
    一轮或一个子 agent 的开销。
  - **多次独立审查取并集**：数据显示这是提升召回最直接的办法（单次约四成，并集 7/8），
    但时间和上游用量都成倍增加，与 plan 128 的速度约束冲突。
  - **降低验证实验的要求**：B 组不做实验也找到了同样多的缺陷，而且更快。但 kloop 的验证
    条款来自 gpt 上的实测问题（plan 119、122），只对 DeepSeek 放宽需要按模型区分 skill。

### 审查顺带发现（不在已知答案里）

- **已确认**：`/context` 的逐块明细仍按 base64 字节估算图片
  （`rust/crates/core/src/commands/context.rs:186` 的 `block_tokens`），与同一命令的
  history 行（每图固定 1,600）和 DESIGN 矛盾。R4 上 4 组全部报出，HEAD 仍未修。
- **待验证**：循环绑定之后包装器分析看到字面值、风险检查仍看到 Unknown，R3-A 给出
  `for t in 'cat .env'; do env -S "$t"; done`，R3-E 给出 `for w in shred; do env "$w" notes.txt; done`，
  两者都指向“父提交硬拒绝、现在放行”。当前 HEAD 的 `env -S` 仍走 unsupported wrapper
  分支且不补 `rewritten_execution()`（`shell/facts.rs:265-280`），需要实际跑权限检查确认。

## 实施（2026-11-09）

用户要求“按最合理的方案做，在保证好的前提下尽量快，并修复发现的 bug”。速度慢和排除
那一步这次都不改：前者换来的是经过验证的结论，验证条款来自 gpt 上的实测问题，要按
模型拆 skill 并在两边重测才能动；后者唯一可能有效的结构性修法会让每次审查多一轮，
与“尽量快”冲突，而漏掉的条目本来就以带理由的形式留在 Excluded 里，读者可以推翻。

- **P1 ✅**：`code-review` skill 无目标时写明包含未跟踪文件，先 `git status --short`
  再全文读新文件；承重条款测试加 `does not show untracked files`。
- **P4 ✅**：bash/PowerShell 输出超出 30,000 字符时，先把捕获到的全文写进 offload 存储
  （与大结果落盘同一入口），截断说明里给出路径、字符数和行数；内联部分不变。每个流的
  捕获上限从 150,000 字节提到 1 MiB，并不再按上限预分配，免得大 diff 落盘也是残缺的。
- **修复 `/context` 图片估算**：history 新增 `estimate_block_tokens`，复用
  `estimate_message_tokens` 的逐块规则；`/context` 的分行明细改用它，顶层图片和工具结果
  内嵌图片都按固定 1,600 计，不再序列化 base64。
- **修复 `env -S` 绕过与循环绑定的危险判定回归**：先用权限层探针确认（修复前
  `env -S 'cat .env'`、`-S'…'`、`--split-string[=…]` 及循环写法在 manual/bypass 下都放行；
  `for w in shred; do env "$w" notes.txt; done` 与 `for w in rm; do env "$w" -rf build; done`
  在 manual 下不经确认放行，而字面写法会问）。
  - `env` 遇到 split-string（含附着值、带 `S` 的短选项簇）标为 `arguments_unknown`，由事实层
    生成未知执行体，按无法排除的敏感读取硬拒绝。`env -S 'ls -la'` 这类良性写法随之被拒，
    其余未知 `env` 选项（`-P`、`--debug`、`-v`）探针确认原本就被近似剥离拦住，不改。
  - 危险判定在 `risk_argv()`（未知词视图）之外再看 `syntax` 求值后的视图，任一危险即确认；
    不改 `value` 保持 Unknown 的设计，所以不产生任何授权。

**审查跟进（同日）**：复审指出三处。一是未知选项提前返回，`env --debug -S 'cat .env'` 的
`-S` 没被检查；现在未知选项之后的任何词像 split-string 都按未知执行体处理，并补上 GNU
长选项缩写 `--s=…`。二是“簇里含 `S`”的判断把 `-uSSH_AUTH_SOCK` 的变量名当成选项，正常
命令被硬拒；改为逐字母解析，带操作数的字母（`u`、`C`、`P`、`a`）之后整簇是值。两条新回归
在上一版 `shell.rs` 上先红后绿。三是基准脚本：本机配置里已有 `system_prompt_file` 时，
临时 HOME 缺提示文件会启动失败，`--system-prompt` 又会追加重复键；现在相对路径的提示文件
随配置复制，显式参数替换顶层键并用 tomllib 校验，三种配置形状用临时目录验证过。

验证：新增与改写的回归覆盖落盘文件全文与内联上限、不超限时不写文件、`/context` 的
图片行与嵌套图片行、split-string 六种形状（manual/bypass）、两条循环包装危险命令的确认、
包装器分析对 split-string 的标记；`kloop-core` 中 `tools::bash`、`commands::context`、
`skills`、`permissions`、`shell`、`history` 相关 349 项在外层执行沙箱之外通过；
`cargo fmt`、`kloop-core` 全目标 clippy `-D warnings` 通过。未跑 workspace 全量测试、
parity 与真实 API；PowerShell 的 Windows 专用测试只按签名核对，未在 Windows 上运行。
