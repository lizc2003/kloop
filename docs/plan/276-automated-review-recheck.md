# Plan 276 — 自动准备独立审查复核 ✅

> 2026-11-10。用户同意继续验证去掉人工候选整理后的收益。

## 范围

在 benchmark 外层实现“真实初审 → 结构化候选账本 → 自动冻结证据 → 独立复核”。
遵守 plan 230，不向共享 agent 循环、工具调度或内置 skill 加入 review 状态。
本次不接入生产 `/code-review`。

- 初审沿用内置审查正文，仅增加实验用机器可读账本；A、B 共用同一次初审。
- 账本里的问题、裁决、理由和源码锚点由初审产生，不人工补候选或选片段。
  仅复核 excluded；空清单不发复核请求，缺账本、格式错误不得当空清单。
- 用户给定目标先固定为 SHA；证据只从它和第一父版本读取。按固定窗口收集锚点
  及另一版本对应位置，去重合并，不读后来的修复。超预算明确失败，不静默裁剪。
- 独立请求隐藏原报告、原裁决和排除理由。证据不足返回 unresolved，不能猜缺失调用。
- 用本机接收端捕获实际 kloop 请求，复用解析后的模型、采样和输出预算；传输限制按
  当前 provider 的 300 秒开流、900 秒空闲、1,800 秒正文截止执行。失败保留、不重试。
- 记录包含初审、证据准备和复核的总时间，以及每阶段交付和 usage；机器引用校验
  不能替代人工检查触发条件和论证。

## 验证协议

先完成局部回归，再选此前四份手工材料以外的两个历史提交，各做一次初审和至多一次
复核。目标选定后冻结协议，不因初审没产生候选或复核无收益而换样、补问题或改窗口。
后续修复仅在运行后用于人工评分，不给模型。只报告这两个配对样本，不外推总体召回。

已冻结目标：`388db36`（worktree）与 `878fe53`（问答显示），均未用于此前四份手工包。
每个目标一次初审、最多一次复核；80 轮 / 3,600 秒初审上限，锚点前后各 80 行、
整包 160,000 字符，不因结果调整。运行捕获和原始报告只放临时目录。

## 完成记录

### 实现与局部验证

- 新增 `scripts/review_pipeline.py`，由 `review-bench.py pipeline` 显式调用。初审的
  机器账本包含原裁决、理由和固定源码锚点；复核只接收 excluded 的中性问题与自动
  准备的代码。A、B 共享同一次初审，未更改内置 skill 或共享循环。
- 锚点必须指向固定 Git blob 的真实行；收集对应前后版本的窗口，跨候选合并重叠
  源码并共享引用。缺文件/空文件显式标注，超预算、缺账本、坏锚点明确失败。
- 本机捕获真实二进制解析后的采样字段；新入口没有另设 8,192 或 high。
  复核传输补齐 SSE 多行帧、原始流捕获和正文硬截止；旧手工入口默认预算保持原义。
- `pipeline-recheck` 只恢复已完成初审、尚未尝试复核的材料阶段。核对原报告/账本，
  沿用原 SHA、窗口、字符预算、配置摘要和采样字段，另建输出目录，保留原失败。
- `python3 -m unittest discover -s scripts -p 'test_review*.py' -v`：29 项通过，含
  真实子进程 + 本机 HTTP、版本冻结、原裁决/鉴权隔离、跨候选去重、坏账本、空清单、
  正文截止、恢复与拒绝请求重试。另以真实 kloop 二进制完成本机请求探针。
  未编译 Rust、运行 workspace 全量测试或 `make check`。

### 真实运行及保留的失败

两组均捕获到正常配置的 65,536 输出 token、xhigh。初审的 80 轮 / 3,600 秒是本轮
明确设置的实验边界，不是正常 kloop 默认；原生初审的内部传输策略沿用运行时。

第一次本机探针模拟流缺关闭事件，被真实二进制拒绝，两组均在初审前停止；未发真实
API 请求。补齐事件并先单独通过真实二进制探针，保留原两份失败，再执行冻结样本。

| 目标 | 初审 | 自动材料 / 复核 | 可验收新增缺陷 |
| --- | --- | --- | --- |
| `388db36` | 73 轮，798.3 秒；3 confirmed、12 excluded | 初版跨候选重复窗口导致 187,677 字符，超过 160,000，未请求复核。修正去重后 116,394 字符，从原报告恢复一次复核，207.1 秒交付 | 0；3 个新增 confirmed 中，1 个明确误报、2 个论证不足 |
| `878fe53` | 80 轮触顶，835.3 秒，退出状态 max_rounds | 无最终报告与账本，未发复核请求，未换样或提高上限重跑 | 未取得可评分对照 |

窗口去重修复保留了相同源码行集合，未人工改问题、锚点或挑片段，也未提高字符预算。
恢复前另冻结修复版本；原材料失败继续保留。它验证了恢复入口，不能描述成两组首次
无人干预就全部完成。

worktree 复核结果为 3 confirmed、7 excluded、2 unresolved。逐条审阅：

- C4 明确误报：声称 closed `TaskTracker::spawn_on` 会 panic/拒绝任务；锁定的公开依赖
  实现仍允许登记和 spawn，关闭只参与 wait 完成条件。初审已经正确排除这个问题。
- C7 观察到回滚吞错误属实，但只说“如果 Git 失败”，未给出具体失败条件与相对基线/
  修复范围的可操作影响，不替模型补触发条件，不计新增有效 finding。
- C8 把“没有等待进程回收”当成“进程仍在写”的论据，没有建立实际写入时序与失败
  触发。后续修复确实处理过 initializing lock 等清理问题，但那不是该回答给出的
  论证，不能因候选方向接近真问题就算救回。
- 7 个排除的主要结论可接受；C11 对前台成功后取消路径的附带描述不完整，C13 把
  “保留了足够诊断”说成“完全没丢诊断上下文”，不能算所有解释都正确。2 个
  unresolved 保留为证据不足，没有改算排除或正确命中。

后续修复只在交付后用于评分：两条主要修复路径（失败 add 删并发创建者资源、成功
结果无人接收时保留位置丢失）初审已报；取消时尚未取得删除权的另一条路径未进入
排除清单，复核也没有补回。此处不据少量样本计算整体召回率。

### 成本与结论

worktree 自动取证恢复耗时 0.8 秒；包含原初审、失败准备与恢复的累计执行时间
1,009.7 秒，不含修脚本间隔。由初审协议落盘到恢复交付的实际经过时间约 1,324.3 秒。
不能把恢复后的 207.1 秒说成整条审查只需这么久。

两次初审记录到 153 次 usage：未缓存输入 347,738、缓存读取 13,848,704、输出
184,633 token。追加复核一次：输入 32,565（缓存 0）、输出 25,043，其中推理 23,893。
总已知输出 209,676；初审未交付的样本也计成本。本机模拟探针不计真实 API 用量。

结论：自动候选/材料/报告与恢复入口已实现，但本轮没有获得可验收的新增缺陷，反而
出现错误确认；继续保留显式实验入口，不接入生产 `/code-review`。下一项有效验证应
先解决依赖语义等缺证据时仍强行确认，以及初审交付边界，不能直接扩大自动提升范围。

## 运行入口与限制

```sh
python3 scripts/review-bench.py pipeline <out-dir> --commit <rev> --kloop <absolute-kloop-path>
python3 scripts/review-bench.py pipeline-recheck <initial-out> <new-out>
```

`--config` 默认 `~/.kloop/config.toml`。`--context`、`--max-chars` 是显式实验参数，
须在采样前冻结；输出上限和 effort 不另设默认，来自真实二进制的本机捕获。
`protocol.json`、`ledger.json`、`packet.json`、`report-a.md`、`report-b.md` 和阶段元数据
保留在输出目录；临时配置副本在退出时删除。真实进程验证遵守外层沙箱约定。

引用通过只代表引用确实落在所供源码中，不代表触发例子成立。结构化账本也不保证初审
记下了每个调查过的候选；固定窗口可能缺跨文件路径，重命名前路径不会自动追踪。
缺证据应 unresolved。A 也带实验账本要求，不是完全未改动的生产审查基线。
